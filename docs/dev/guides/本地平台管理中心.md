# 本地平台管理中心

> 状态：可试用｜最后更新：2026-08-01
>
> 本文是开发者在单机启动完整平台管理中心的操作真源。生产节点接入仍以《[Linux 节点 SSH 首次引导](Linux节点SSH引导.md)》为准。

## 1. 一键启动

环境需具备 Go、C 编译器、Node.js、pnpm 和 curl。无需单独安装 NATS、Vault 或数据库。首次运行或环境变化后先执行：

```bash
./engineering/tools/platform-dev.sh doctor
```

全新空环境先交互设置数据库无关的 Seed 管理员，再显式建立一次平台基础组合：

```bash
./engineering/tools/platform-dev.sh seed-admin init --operator <管理员账号>
./engineering/tools/platform-dev.sh bootstrap
```

未指定 `--password-file` 时，入口调用 `engineering/tools/create-seed-password-file.sh`，从控制终端静默读取并确认两次密码，创建 `0600` 临时文件；初始化无论成功或失败都会删除该文件。非交互环境不会等待输入，必须显式提供 owner-only 密码文件。

初始化完成后，人机入口显示 generation、phase 和更新时间的友好摘要，并给出 `bootstrap --rebuild-seed` 下一步提示；底层 `seedaccessctl` 默认仍输出 JSON，自动化可继续稳定解析。

如果平台基础组合早于 Seed 管理员初始化，随后执行的显式 `bootstrap` 会根据稳定主体补齐 `platform.seed-owner` Role/Binding、重新签发授权快照，并在 Policy 服务首次受信调用时把同一 Seed Authority 基线原子同步到 Shared State；同名保留 ID 已被非 Seed Authority 对象占用时会拒绝协调。普通 `up/restart` 仍只恢复已发布状态，不承担这项授权修复。

显式密码文件是仅包含密码原文的普通文本文件，不是 JSON/YAML；规范化后必须为 12–1024 字节。初始化与登录使用同一个密码协议裁剪首尾 Unicode 空白（包括空格、Tab、CR/LF），内部空白仍属于密码内容。文件只由本机初始化工具读取，不会进入命令行参数、日志、Provider Catalog 或 Portal Session。初始化完成后可安全销毁外部提供的文件；`seed-admin status` 只显示 generation、phase 和更新时间，不返回账号或 verifier。Seed Access 不提供默认密码，也不能重复初始化。

后续普通启动只恢复已发布状态，不创建任何新 revision：

```bash
./engineering/tools/platform-dev.sh up
```

`bootstrap` 默认复用已经验证的 stable Seed Runtime，只重新物化配置 Catalog，并显式发布平台 Deployment 与初始 Portal Activation。显式发布阶段会短暂启动只绑定回环地址的开发发布端，使用作者、审批者和发布者三个隔离会话完成治理流程；发布端随后关闭，正式 Portal 再以 Authentication Broker 模式启动。普通 `up/restart` 不创建发布端。首次没有 LKG 时才执行安全初始化构建；只有准备晋级新的 stable refs 时才使用 `bootstrap --rebuild-seed` 重建 Backend、Portal 和最小插件集合。平台完全收敛后，新的候选才会提交为内容寻址的 Last-Known-Good。`up/restart` 只恢复该快照并用本次运行的临时密钥重新签署相同包体，不重建、打包或发布当前工作区插件，也不触碰 stable 身份账本。

Seed LKG 的提交边界位于平台三阶段收敛之后、初始 Portal Activation 之前。若 Portal 已有内容不同的未完成 Publication，`bootstrap` 会保护用户数据并返回失败；此时 Seed LKG 已保持与新 Deployment 一致，可直接使用 `up` 恢复服务，再从 Portal 治理页面处理冲突。

开发编排器的增量构建从真实 Go 依赖图读取本仓库包目录，同时跟踪包内可能被 `go:embed` 编入二进制的 Schema 等文件，不再手工维护目录白名单。契约或内部依赖变化后不得复用旧编排器，否则本地插件自发现可能对新 Manifest 产生错误的兼容性结论。

Local Plugin Library 会在控制器每次启动时重新尝试一次已持久化的失败源码。这样即使插件目录内容没有变化，修复契约、构建器或本地仓库依赖后也能自动恢复；同一次运行内若仍失败则保持静默，避免持续构建风暴。

源码控制器启动时会等待 local-test 仓库真正可连接，再读取既有 workspace 候选；不会因为内核已就绪而仓库 Socket 尚未创建的短暂竞态永久退出。

开发引导的 Portal 初始发布仍使用作者、审批者和发布者三个独立主体。它们的签名 Bootstrap Grant 必须直接消费当前 Permission Catalog 中的 `platform.portal.read/compose/approve/publish`；不得依赖 Session 内的旧角色名或管理员旁路完成 Backend 授权。

后台模式中，platformdev 会在启动任何子进程前创建独立会话，并继续持有所有长期子进程的显式生命周期；Portal Kernel、Backend Kernel 与 Runtime Host 还会使用独立进程组。这保证脚本返回或终端关闭不会向编排器及受管子进程误发 `SIGHUP`；正常停止仍由 `platform-dev.sh down` 通过编排器优雅收敛。`--debug` 前台模式不脱离当前终端，保留 `Ctrl+C` 调试体验。

显式平台 apply 是可重试的状态协调，不是“每次从头发布”：它按 Portal 的 `WorkingCopy → PendingApproval → Approved → Published Publication → Current Release` 持久状态继续剩余步骤。幂等判断覆盖完整 Portal 配置（Application、Platform Profile 与管理服务绑定），三者都未变化且已成为 Current 时才 no-op；Platform Profile 或服务绑定变化即使页面 Application 未变，也会形成新的受治理版本和 Release。内容不同的未完成候选会 fail-closed，历史已上线内容必须走 rollback，工具不会自动覆盖或伪装回滚。Test Release 候选不进入该正式治理视图，因此 testing/workspace 制品不会被平台 apply 复制到稳定基线。

已有开发状态升级到本机制时，会且只会迁移 `actual-state.json` 正在引用的完整历史运行；不会误选时间更新但未启动成功的目录。全新空环境直接执行 `up` 时允许完成一次无业务发布权的安全初始化构建。Seed 插件源码变化通过 `dev-plugin` 生成 workspace 候选；准备稳定晋级时先提升 SemVer 和 Profile 精确引用，再执行 `bootstrap --rebuild-seed`。就绪后打开：

状态脚本优先使用 owner-only PID 文件；若 PID 文件丢失且当前环境限制 `ps`，只允许通过开发网关监听端口定位候选 PID，并使用该进程打开的可执行文件反查确认它确实是当前工作区的 `platformdev`，确认后才恢复 PID 文件。不得仅凭端口占用或可发送信号就接管进程。

<http://127.0.0.1:18080/operations>

常用命令：

```bash
./engineering/tools/platform-dev.sh status
./engineering/tools/platform-dev.sh logs
./engineering/tools/platform-dev.sh logs --follow
./engineering/tools/platform-dev.sh restart
./engineering/tools/platform-dev.sh down
```

`status` 同时返回 `productionEquivalent: false`，避免把开发夹具误认为生产部署证明。
`startupPublication` 只有显式 `bootstrap` 进程为 `true`；普通 `up/restart` 必须为 `false`。
`identity.protocol` 默认是 `broker`，浏览器没有有效 Session 时必须进入 `/auth/access`。只有纯 UI 调试可以显式使用 `up --auto-login`；此时 `identity.autoLogin=true`，启动日志会持续标明管理员旁路，不能作为认证、权限或发布流程的测试结果。

前端插件事务式热替换默认开启。编排器从产品与示例插件的 `vastplan.plugin.json#entry.frontend` 自动发现 UI 插件；新插件只需将源码置于 `frontend/src/index.(tsx|ts|jsx|js)`，并将产物入口声明为 `frontend/dist/` 下的 JavaScript 文件，无须修改开发工具中的插件名称列表。修改 `extensions/plugins/*/frontend/src/` 或 `examples/plugins/*/frontend/src/` 下的 TypeScript、TSX、CSS 或 JSON 后，编排器会构建一套候选模块；浏览器完成摘要校验、完整 Portal 装配和可选状态恢复后原子切换，不刷新文档。构建或装配失败时当前页面继续运行，并在页面右下角显示失败原因。`status` 的 `hotGeneration` 与 `hotError` 可用于诊断最近一次候选。

本地 Platform Profile 同时设置 `updates.mode=automatic`。经托管测试仓库和 Frontend Test Release 产生的真实新 Activation，会由 Node Portal Kernel 在完整预取后通过认证 SSE 通知已打开页面。兼容变更无刷新提交 Portal Generation；Renderer 或共享 UI 契约边界先预验证、再刷新 Host Epoch，失败时启动上一安全 Activation 而不循环刷新。生产 Profile 未显式选择时仍默认 `refresh`，浏览器不连接更新事件，也不轮询。

开发态 HMR 将 Foundation Renderer、Shell、Workbench 的模块图和 RuntimeSpec `uiContract` 放入同一 Generation 原子覆盖。同一契约族的源码 Manifest 未全部同步时，候选 Generation 会被拒绝，不再把新版模块装入旧 Profile。Module Graph 在生成器、Go 签名校验器与浏览器加载器中统一按 UTF-8 字节序规范化，禁止使用受区域设置影响的排序。公共 UI Contract 版本发生变化后，仍需执行 `./engineering/tools/platform-dev.sh bootstrap --rebuild-seed`，把仓库中的新插件 SemVer、Platform Profile revision 与 Activation 正式同步；普通 `up/restart` 坚持零发布，不替代这一步。
开发网关的 `/__vastplan_dev/runtime` 在调用方未传 `path` 时固定投影为 `/operations`，与当前本地管理 Portal 入口保持一致；显式 `path` 仍原样传给 Portal Kernel。

启动器还会校验并物化 `engineering/deploy/portal-access-profile-catalog.json`，核对其 Frontend Platform Profile 精确锁后交给 Node Portal Kernel。可用下面的只读端点检查会话前目录是否生效；响应只包含公开品牌、语言、方法策略与 Generation ID，不包含 tenant 或内部插件引用：

```bash
curl 'http://127.0.0.1:18080/auth/v1/bootstrap?returnTo=/operations'
```

开发网关在热加载开启时也会把页面、`/auth/*` 和 API 请求转发给 Node Portal Host；HMR 只接管摘要绑定的开发资产与 Runtime 投影，不能成为第二个无鉴权页面服务器。`/auth/access` 已运行统一语义 AuthenticationFlow，会按 Access Profile 显示企业选择的认证方式。初始默认方法是 `seed-password`，正常登录通过 Broker Assertion 和 Authorization Session 建立会话；Provider 管理页的测试操作会进入隔离测试事务，完成真实认证但不签发或替换平台会话。

认证完成后浏览器会得到相互绑定的 `vastplan_session` 与 `vastplan_auth_proof` 两个 HttpOnly Cookie：前者承载平台主体和授权快照，后者只保留 Seed 交接等敏感操作需要的短时认证证明。拆分用于遵守浏览器单 Cookie 大小限制，不代表两套会话；缺少或错配证明只会禁止需要新鲜认证证明的操作，不会放宽普通会话校验。

开发编排器使用两个职责不同的制品来源：

- `https://127.0.0.1:18442` 是随本次运行创建的 Seed 仓库。`.vastplan/dev-platform/runs/<run-id>/repository/`、Profile、TLS 和 `local-development` 签名身份均为临时数据，只用于自举平台基础单元；
- `artifact.repository.local-test.v1` 是由 `cn.vastplan.platform.artifacts.repository` 提供的 Local Plugin Library。它只监听 `.vastplan/dev-platform/repositories/testing/repository.sock`，Socket 为 `0600`，逐次运行令牌保存在当前 `runs/<run-id>/secrets/`；File Volume 与 `local-testing` 签名身份仍保存在 `.vastplan/dev-platform/repositories/testing/`，普通重启后继续存在。它既接收本地 `workspace/testing` 构建，也可保留上游身份地导入 remote.v1 精确制品。

Seed 不扫描并签署源码树中的全部插件。`bootstrap` 只在 Profile refs 与 LKG 一致时复用既有 stable 包；refs 变化会明确要求 `--rebuild-seed`。显式重建的选择计划由平台配置和 Manifest 依赖闭包自动生成，额外制品、版本不一致或 stable 身份漂移会在候选提交前 fail-closed，并一次列出全部冲突引用。普通 `up/restart` 只复验活动快照。插件快速调试使用 `dev-plugin`/`workspace`，完整测试使用 `publish-test`/`testing`。

默认热开发模式还会启动 Local Plugin Library 源适配器。它监视 `extensions/plugins` 与 `examples/plugins` 的直接子目录：新目录或源码保存后，防抖、构建并发布新的 workspace 候选；删除目录或被新候选替代时，向 Catalog 写入 `artifact.withdrawn`，不直接删除包体，也不自动修改任何服务或 Portal Activation。状态端点的 `pluginLibrarySource` 字段可查看各目录的 `Observed/Building/Publishing/Ready/Withdrawing/Removed/Failed` 状态。首次启用只记录现有源码基线并接管已有 workspace 候选，不在平台启动路径批量重建全部插件；使用 `--no-hot` 可同时关闭该自动源码适配器，显式 `dev-plugin` 和 `plugin-release` 仍可使用。

ADR-0160 首次引入 Assignment 精确 SHA-256，旧开发 NATS 状态不再兼容。已有 `.vastplan/dev-platform` 的工作区只需在切换到该契约时显式执行一次 `./engineering/tools/platform-dev.sh bootstrap --rebuild-seed --fresh`；之后普通启动继续复用 LKG，不需要重复清理或重建。

托管仓库的 File A/B 在线迁移状态保存在 `repositories/testing/control/repository-migration.json`，物理卷位于 `repositories/testing/volumes/`。管理 BFF 以 `prepare/sync/cutover/rollback/finalize/release` 显式阶段开放，迁移状态只以脱敏摘要进入 Workbench。`release` 会在配置已切到目标 volume 并重启后才生效，且只把旧卷移入 Provider 私有 quarantine，不立即删除。制品级 GC 另使用仓库 volume 内的 `catalog/garbage-collection.json` 恢复隔离/清扫进度；只接受先显式 yank/revoke、再 plan、再隔离至少 24 小时、最后复核 sweep 的路径。

开发 Profile 默认给托管仓库设置 10 GiB/10000 个活动制品的全仓上限，并给 `testing` channel 设置 5 GiB/5000 个的累积上限。目录、容量/配额、引用快照和 GC 已统一为 Workbench Collection 页面，通过制品仓库三级导航访问。具有 `platform.artifacts.gc` 权限的调用方才可执行隔离和到期清扫；开发管理员由 Seed 物化为 `platform.owner` Role/Binding，并从当前 Permission Catalog 取得精确权限，不再使用 `platform.admin` 兼容映射。配额拒绝不会自动删除任何数据。

每次启动都会分别生成 Seed-only、testing-only 和只供 Node Agent 消费的组合信任快照。Seed 仓库不接受测试发布身份，托管仓库也不接受临时 Seed 身份。两个 Node Agent 先按精确 ref 查询本地签名 Seed，未命中才通过 local-test Adapter 访问托管测试仓库，并对两类来源做相同的内核复验。消费 Inventory 不自动取得发布权限：只有平台 Node Agent 显式承担 `publish-bootstrap-references` 职责，其传输身份也只允许精确的 `bootstrap-inventory/local-seed` SYSTEM 子身份；managed-services Node Agent 只消费同一清单。测试签名私钥不会注入仓库或 Node Agent；后续发布工具只应在受控的本机测试发布路径中使用它。`VASTPLAN_DEV_SEED_ARTIFACT_PORT` 仍控制 Seed HTTPS；`VASTPLAN_DEV_ARTIFACT_PORT` 仅在显式 `VASTPLAN_DEV_ARTIFACT_PROTOCOL=remote-compat` 诊断模式下使用。

正常开发不应启用 remote 兼容模式。只有排查迁移差异时，才可在平台停止后临时执行 `VASTPLAN_DEV_ARTIFACT_PROTOCOL=remote-compat ./engineering/tools/platform-dev.sh bootstrap`；该模式仍使用同一个持久仓库，不会创建第三份数据，但继续承担回环 TLS 与分离 HTTP token 的兼容成本。

平台 Node Agent 默认启用 `-bootstrap-upgrade`；普通消费节点不启用。当仓库关键栈的目标版本不在 Seed、但已存在于托管仓库时，可信宿主会先把已验签候选与证明复制进 Seed，再启动候选；只有真实运行健康且 Assignment 引用发布成功后才推进 `seed-inventory.json` 的 LKG。Seed/LKG 引用使用当前 Deployment 的可信租户，不使用可绕过传输身份租户边界的伪全局租户。失败候选只会扩展 Seed，不会覆盖旧 LKG。该开发默认值不代替生产目录权限和 systemd 内核升级规划。

开发编排器还会生成 `recovery-capsule.json`，启动 Backend 的 loopback Recovery 端点并把 Portal Host 固定连接到该端点。`http://127.0.0.1:18080/recovery` 不依赖 Portal Activation、Workbench、设计系统或插件前端模块；`/__vastplan_dev/status` 的 `recoveryCapsule` 使用同一共享状态契约。开发模式允许测试仓库 Bootstrap Upgrade，生产 Recovery 节点则必须使用配对 Capsule 的发行事务。

临时排查热替换自身问题时可以关闭它；该参数同时让 Portal Shell 不连接开发事件源：

```bash
./engineering/tools/platform-dev.sh restart --no-hot
```

需要在终端直接观察完整构建与运行日志时使用调试模式；`Ctrl+C` 会由编排器按依赖倒序关闭受管进程：

```bash
./engineering/tools/platform-dev.sh up --debug
```

### 1.1 Backend 插件保存后热切换

平台完成 `bootstrap` 且目标服务已经发布后，可在独立终端启动一个 Backend 插件开发控制器：

```bash
./engineering/tools/platform-dev.sh dev-plugin \
  cn.vastplan.example.backend.quota \
  --backend-target managed-services/quota-service
```

也可以把第一个参数写成 `extensions/plugins/<plugin-id>` 或 `examples/plugins/<plugin-id>`。控制器从 `vastplan.plugin.json` 自动识别 Go 原生、dynamic-go、Node Worker、Python 进程或 Python 子解释器，不维护插件白名单；`--backend-target` 必须指向已发布 Application 中允许测试替换的应用插件槽位。已有管理员绑定时可补充 `--backend-binding <id>`。

启动后会立即构建一次，之后轮询源码、锁文件、协议和对应语言 SDK。连续保存先防抖，旧构建尚未提交时可以取消；每个有效输入生成不可覆盖的 `dev.workspace.<source-digest>` 包，经 local-test/workspace、完整 Test Release 和 Service Generation 原子切换。构建或候选失败保留上一可用代。`Ctrl+C` 只停止该监听器，不停止平台，也不回滚已经提交的候选。

`platform-dev.sh status` 的 `backendPluginDevelopment` 会列出最近的 `Debouncing/Building/Publishing/Ready/Failed`、generation、源码摘要、候选版本和失败原因。状态文件位于 `.vastplan/dev-platform/plugin-dev/status/`；构建目录和候选包位于同一 state root，均不进入 Git。本入口只允许当前 local-development 平台；平台未运行、仓库/目标未就绪或使用 remote 协议时直接拒绝。

### 1.2 发布测试制品

待测试插件必须先由对应语言构建器产出入口，并将清单、Backend 握手身份和前端 RuntimeSpec 统一为唯一 `dev.*` SemVer 预发布版本，例如 `0.4.0-dev.20260720.3.a81c33f`。随后用 `pluginpackage` 生成包，再通过受控入口上传：

```bash
go run ./engineering/tools/pluginpackage \
  -source examples/plugins/<plugin-id> \
  -backend-bin <已构建入口> \
  -out /tmp/<plugin-id>.tar.gz

./engineering/tools/platform-dev.sh publish-test /tmp/<plugin-id>.tar.gz
```

`pluginpackage` 会从最终 Go 二进制、Node/Frontend 构建器保留的 metafile 或 Python PEP 751 标准锁自动生成并绑定插件 SBOM；Python 锁和全部本地 wheel 必须闭合，缺少真实构建证据会阻断打包。若测试的是工作区外插件或尚未接入自动取证器的语言，必须显式使用 `-sbom` 提供 CycloneDX 文档。

含 Frontend 的插件先运行 `pnpm build:frontend:plugins`，再使用构建器生成的可信图打包；`-frontend-bundle` 仅保留给旧单文件迁移输入：

```bash
plugin=examples/plugins/<plugin-id>
go run ./engineering/tools/pluginpackage \
  -source "$plugin" \
  -frontend-graph "$plugin/frontend/dist/vastplan.browser-graph.json" \
  -frontend-graph-root "$plugin" \
  -out /tmp/<plugin-id>.tar.gz
```

打包器会逐节点复算大小和 SHA-256 后把 Graph 注入最终签名 Manifest；仓库接收和每次读取制品时由 `artifacttrust` 再次扫描 tar 实际字节。缺失节点、替换内容、路径逃逸、未知外部依赖或 graph digest 漂移均 fail-closed。

`publish-test` 不接受任意仓库地址、channel、key ID 或命令行 token。它从受管运行目录读取精确 Repository Profile 和 owner-only 短期令牌，默认只连接 local-test Unix Socket，使用 `local-testing` 身份签名并强制 `testing` channel；返回前还会重新读取 Envelope、复验发布者证明与包内容，并确认带 Profile 身份的精确回执和 repository revision。若仓库服务尚未通过显式 `bootstrap` 发布，命令会直接提示仓库未就绪，不会在启动过程中暗中发布平台服务。

只上传、不改变运行服务时使用上面的命令。要把同一份精确回执继续提交给 Backend Test Release Controller，可选择以下一种方式：

```bash
# 首次或日常开发：自动创建/校准仅限本地开发的目标绑定
./engineering/tools/platform-dev.sh publish-test /tmp/<plugin-id>.tar.gz \
  --backend-target managed-services/hello-service

# 复用平台管理员已经创建的绑定
./engineering/tools/platform-dev.sh publish-test /tmp/<plugin-id>.tar.gz \
  --backend-binding dev-or-admin-binding-id
```

`--backend-target` 的格式固定为 `deployment/unit`，插件 ID 来自已验签制品，不能由命令行替换。CLI 用本地管理员身份保存绑定，再用独立发布者身份提交 Test Release；候选失败会返回非零，并报告已经安全回滚还是仍需人工恢复。该便利入口只在状态端点证明目标为回环、`local-development` 且非生产等价模式时启用。生产环境必须由管理中心显式预授权 binding，不能复用这些固定开发会话。

Frontend 功能插件已在 Application 中时，使用：

```bash
./engineering/tools/platform-dev.sh publish-test /tmp/<plugin-id>.tar.gz \
  --frontend-target operations
```

Renderer、Shell、Workbench 或当前属于 Platform Profile 的平台管理 UI，必须显式选择专用测试 Profile：

```bash
./engineering/tools/platform-dev.sh publish-test /tmp/<plugin-id>.tar.gz \
  --frontend-target operations \
  --frontend-scope platform-profile-plugin
```

后一种方式会生成 tenant 专用的新 Profile 和 Binding revisions，不会改写共享平台基线。成功后新 Activation 已由 Backend `portaltrust` 物化，并可由 Node Portal Kernel 冷填充；当前生产语义是用户刷新时加载，测试开发态可使用自动 Generation/Host Epoch 切换。

需要丢弃旧的运行目录、持久测试仓库和构建缓存并重新建立平台基础组合时显式使用：

```bash
./engineering/tools/platform-dev.sh bootstrap --rebuild-seed --fresh
```

准备把 Seed 变更晋级为 stable 时，必须同步提升插件 SemVer 和 Profile 精确引用；统一目录插件引用的内部模块版本变化时，两者同代升级。随后使用 `bootstrap --rebuild-seed`。已登记的 stable 精确引用会从 `.vastplan/stable-packages/` 按 SHA-256 复验并复用，当前工作区中未提升 SemVer 的变化只产生“未晋级”提示，不会覆盖旧包；身份账本和对象缓存均不随 `--fresh` 或 `clean` 删除。日常源码调试使用 `dev-plugin`/`workspace`，完整测试使用唯一 `dev.*` 预发布版本。

`--timeout <秒>` 可覆盖默认 300 秒启动等待。脚本只检查并管理 `.vastplan/dev-platform/` 对应的进程，不会像通用端口清理脚本一样终止其他项目的端口占用者；端口冲突会在耗时构建前直接失败并显示占用进程。

### 1.3 从远端仓库安装到本地插件库

本地平台就绪后，可以把 remote.v1 Catalog 中已经存在的精确插件下载到 Local Plugin Library：

```bash
./engineering/tools/platform-dev.sh plugin-library install \
  --remote-profile /secure/enterprise-repository-profile.json \
  --remote-token-file /secure/enterprise-repository-read.token \
  --remote-trust /secure/enterprise-artifact-trust.json \
  --remote-ca /secure/enterprise-ca.pem \
  --plugin cn.example.plugin \
  --version 1.4.2 \
  --channel stable \
  --target backend \
  --kernel-version 0.1.0 \
  --allowed-publishers vastplan
```

命令以精确根 ID、版本和 channel 调用远端 Resolver，取得绑定 Catalog revision 的 Artifact Lock，再校验根、SemVer、完整依赖闭包和依赖环。每个原始 Envelope 都由本地库复验 publisher、SHA-256、证明和供应链状态；如果安全准入或复扫记录引用原始报告，会先从远端按摘要下载并写入本地私有报告归档，报告完整后才导入制品并写入带上游 Receipt 的 `artifact.imported` Journal 事件。相同来源和摘要重复执行幂等；Catalog/Lock/Object 漂移、yanked/revoked、跨 Profile、摘要变化、报告缺失或本地同 ref 不同来源均拒绝。部分下载只会留下可重试的不可变对象，整份锁全部导入成功前不会用于激活；导入本身也不修改 Deployment 或 Portal Activation。

### 1.4 开发构建缓存

本地启动器把构建结果按内容摘要保存在 `.vastplan/dev-platform/build-cache/`，并保留共享的 Go 编译缓存 `.vastplan/dev-platform/go-cache/`。每次运行仍创建独立运行目录，但优先用硬链接装配已验证的不可变产物；文件系统不支持硬链接时自动退回复制。待进行本次运行签名的插件仓库属于可变目标，必须复制装配，禁止通过硬链接反向改写不可变缓存。

完整构建缓存只服务显式 `bootstrap --rebuild-seed` 和无历史快照的首次安全初始化。普通 `bootstrap/up/restart` 直接使用 `.vastplan/dev-platform/state/seed-runtime-snapshots/<digest>/` 中的插件仓库、Runtime Host 和 Portal LKG，但会单独校验并按需刷新与当前开发编排器配对的 Backend Kernel；该宿主刷新不会重建或覆盖 stable 插件制品，服务健康后才晋级新快照。缓存分为 Backend Kernel、逐 Go 插件、Portal/前端插件、dynamic-go 和本地插件制品仓库五类。每个 Go 二进制使用 `go list -deps` 得到真实本地依赖闭包：

- 源码、插件清单、构建脚本或对应工具链版本变化时，只使受影响阶段及其下游制品失效；
- `dist/`、`node_modules/` 等派生目录不参与源码摘要，避免构建输出反过来触发重建；
- 启动器在任何 Node 构建前按 `pnpm-lock.yaml` 执行离线 frozen install，编排器在 SBOM/制品构建前再次复核；本机 pnpm store 不完整时，先手工运行 `pnpm install --frozen-lockfile`；
- 候选产物验证通过后才原子写入完成标记；插件仓库还会逐个复算对象摘要、大小和 tar 内 Manifest 绑定，残缺或被破坏的缓存会自动重建；
- `.vastplan/stable-package-identities.json` 记录每个 stable 精确引用的首次包摘要，`.vastplan/stable-packages/` 保存其复验对象；Seed 重建复用旧对象，源码、依赖或工具链变化只有提升插件版本后才会晋级，删除运行缓存无效；
- dynamic-go 的宿主/插件共同 ABI 指纹只由 Go 工具链、构建标签、模块锁和 Host/`.so` 的实际本地依赖闭包生成，不绑定 Git commit 或无关工作区 diff；该指纹作为 Seed Deployment 输入参与业务 revision 分配，失败重试时相同指纹复用原 revision，实际 ABI 输入变化则先分配更高 revision，禁止出现同 revision 不同精确摘要；
- `restart --fresh` 和 `clean` 会清除缓存，适合验证真正的冷启动。

这套缓存只优化本机开发和测试启动，不定义生产制品仓库、生产数据持久化或跨节点缓存策略。

## 2. 启动内容

普通启动只保证以下最小宿主先就绪：嵌入式 NATS、Backend Node Agent/Controller 的恢复循环、Node Portal Kernel 与开发网关。Node Agent 在首次期望态发布前安静等待；Controller 只观察已有 Deployment，不写入新业务 revision。恢复期间仍会更新 Node/Capability Lease、ActualState、Assignment generation 和制品引用心跳，这些是可过期的运行事实，不是 Deployment 或 Portal 业务发布。启动器还会装配本次运行所需的签名 Seed 读取材料和构建缓存，并从已验签 Seed 制品机械重建缺失的 API Contract Catalog；这些动作不具有控制面业务发布权限。开发 Portal 在宿主就绪、但 Portal Composer 等已发布平台单元仍在恢复时，只对 `502/503/504` 运行描述执行由开发运行协议定义的有界退避重试（最长约 32 秒）；成功后立即停止，非暂态 4xx 直接 fail-closed，生产协议不启用该重试。

执行显式 `bootstrap` 后，平台基础组合包含：

`bootstrap` 中的 `platform-management-profile.json + platform-management-application.json` 只是受信种子配置源，不是另一种服务模型。控制面先把它适配为精确 Catalog binding，再与在线 Deployment Manager 发布一样经过统一的可信预览、摘要锁、Resolver、Deployment CAS 和 Configuration Catalog。普通 `up/restart` 不消费该种子源，只恢复最后一次已发布的 Deployment；未来在线配置则从共享账本读取输入并进入同一发布核心，详见 [ADR-0147](../decisions/ADR-0147-种子与在线服务配置统一发布机制.md)。

配置所有权仍明确分开：`platform-management-profile.json` 的 `services` 只保存种子管理面自举所需的本地插件配置，不会出现在在线配置页；面向受管在线服务的 Profile 使用 `serviceBaselines` 声明公共插件与受保护配置，由“公共基线配置”页面管理；Application Composition 中具体服务的应用插件配置由“服务配置”页面管理。两类在线变更都要经过候选、权限、审批和发布，且服务配置不能覆盖公共基线字段，见 [ADR-0148](../decisions/ADR-0148-公共服务基线与种子配置分域.md)。

- 嵌入式 NATS JetStream、双目标 Controller fleet、平台 Node Agent 和独立 managed-services Node Agent；
- 十六个核心管理服务单元：原有平台管理服务、合并承载 Seed Access 与 Authentication Broker 的认证服务，以及独立 Authorization Session；三项认证能力仍是独立插件，不进入内核业务代码；
- 每个服务单元本地附加的平台管理权限策略；
- 以 `dynamic-go` 内嵌运行的 bootstrap-policy；
- Node Portal Kernel、Ant Design Renderer、标准/顶部布局制品，以及经 Published 输入与 CAS Activation 上线的 `/operations` Portal；
- 仅绑定回环地址的前端源码监听、候选模块端点和 SSE 热替换事件；
- 全局设置、API 暴露、凭证引用、数据库连接、制品仓库和“服务与节点部署”页面；
- 平台预授权的 `local/managed-services` 目标。`hello-service` 不再由启动器创建，必须通过管理中心按业务发布流程显式提交、审批和发布。

Backend 服务页面当前只允许配置 Application Composition；按 ADR-0143 完成 Planner 后将进一步收窄为 Application Intent。Platform Profile、平台插件、控制面 key 和真实路由目标不会出现在该表单中；最终 Deployment v2 预览会显示内核规范化和注入后的结果。Portal 管理中心只提供一个 Portal 工作区：平台 UI 配置、应用组合和服务绑定都属于 WorkingCopy 的内部配置，不再分别管理 Profile、Binding 与 Activation。提交时冻结 Publication，上线与回滚作为 Portal 行内的子流程生成不可变 Release；只有显式配置 Workspace 后才出现版本历史、比较和恢复。

默认 Broker 模式不再创建浏览器管理员旁路。以下固定会话只在显式 `--auto-login` 或 `bootstrap` 的临时发布阶段存在，用于开发发布治理，不得用于认证回归测试：

```javascript
document.cookie = "vastplan_session=vastplan-local-portal-author; path=/"
document.cookie = "vastplan_session=vastplan-local-portal-approver; path=/"
document.cookie = "vastplan_session=vastplan-local-portal-publisher; path=/"
```

这些固定 token 仅存在于绑定 `127.0.0.1` 的开发夹具，生产环境禁止使用。

## 3. 本地安全边界

这个入口只用于开发试用：

- 所有监听地址固定为 `127.0.0.1`；
- 开发网关默认只转发浏览器 Session；Gateway 与内部 Portal Host 都固定为回环 HTTP，使浏览器 Origin、CSRF 和 Cookie 安全语义保持一致。Portal Host 必须显式使用开发专用 `--allow-insecure-http`，生产仍强制 TLS；只有显式 `--auto-login` 才注入本地管理员 session；
- NATS 使用随机本机端口和显式 insecure 开发模式；
- 凭证插件连接仅供本地测试的 Vault Transit 兼容桩；
- Seed 制品仓库只承载本次运行由临时受信任密钥签名的自举制品；托管测试仓库保留跨运行数据，但仍仅用于本机开发；
- 持久测试签名私钥和所有仓库目录必须保持 `0600/0700` 权限，符号链接或宽权限会使启动 fail-closed；
- 所有运行数据位于 `.vastplan/dev-platform/`，已被 Git 忽略。
- 开发模块只保留最近 8 个 Generation，使用独立 URL 解析入口，不写入不可变插件仓库或正式 Portal 快照。

不要把 `18080` 或内部随机端口暴露到局域网、公网或反向代理。生产环境必须使用真实身份提供方、mTLS/NKey NATS、Vault/KMS、签名制品仓库和受控 Linux Node Agent。

## 4. 运行数据与排障

启动日志：

```text
.vastplan/dev-platform/platformdev.log
```

每次运行的制品、安装目录、状态和临时密钥位于：

```text
.vastplan/dev-platform/runs/<run-id>/
```

跨普通重启保留的测试仓库数据与本地测试签名身份位于：

```text
.vastplan/dev-platform/repositories/testing/
```

普通重启还会保留 Portal Composer/Interaction Broker、Deployment Manager、全局设置、凭证引用、数据库连接、Node Agent ActualState 与 Portal 交付源快照：

```text
.vastplan/dev-platform/state/
```

API Contract Catalog 也是从当前签名清单重新生成的派生文件，但使用上述稳定状态目录，而不是带时间戳的单次运行目录。这样同一 Backend Platform Profile revision 在普通重启时保持内容一致，控制面可以安全地幂等重放；内容真正变化时仍必须提升 Profile revision。

这些状态的单调 generation 不会因新建 `runs/<run-id>/` 而回退；单次运行的锁、缓存、临时安装目录和会话密钥仍位于当次 run 目录。显式 `bootstrap/apply` 的插件就绪门不会直接相信保留下来的 `active/ready`：只有 ActualState 在本次 Node Agent 启动后重新写入、目标 unit 均无候选事务且全部就绪，才认定该次显式发布已收敛。普通 `up/restart` 只开放独立的最小内核就绪门，已发布平台插件的恢复不得反向变成启动发布或阻断最小宿主。

该签名身份仅是开发夹具，不是生产发布密钥。`restart --fresh` 与 `clean` 会删除整个开发状态根，因此也会明确删除该测试仓库；普通 `restart` 不会。

`logs` 默认显示最近 100 行，`logs --follow` 持续跟踪；也可用 `logs --lines <行数>` 调整初始行数。后台启动会把编排器的 `[1/6]` 到 `[6/6]` 阶段进度同步显示到终端，失败时自动打印最近日志。

PID 文件失效或 PID 被系统复用时，脚本只清理 PID 文件，不会误杀对应进程；编排器 PID 文件丢失时可从精确二进制路径恢复。异常退出遗留的子进程仅在命令路径位于当前 `.vastplan/dev-platform/runs/` 时才会被回收。

需要删除全部历史运行数据时，先停止平台再清理：

```bash
./engineering/tools/platform-dev.sh down
./engineering/tools/platform-dev.sh clean
```

`clean` 在检测到本项目受管进程仍运行时会拒绝执行。

## 5. 与生产部署的关系

本地启动器验证的是同一套插件清单、Backend/Frontend 双输入组合解析、服务审批与摘要锁、Controller fleet、Node Agent 调度收敛、能力寻址、权限判定、Portal 内容寻址快照和动态模块加载。它有意替换了外部基础设施和登录入口，因此不验证：

- SSH 首次引导、systemd 托管和远端主机故障；
- 生产 NATS 身份、ACL、证书轮换和多节点网络；
- 真实 Vault/KMS、企业身份提供方和签名发布审批；
- 多节点副本、故障转移、容量测试与 Soak。

生产部署流程见《[服务部署控制台](../architecture/服务部署控制台.md)》《[Linux 节点 SSH 首次引导](Linux节点SSH引导.md)》和《[NATS 生产安全](NATS生产安全.md)》。
