# 插件统一升级与发布编排

本指南是公共契约和插件升级的操作真源。架构取舍见 [ADR-0165](../decisions/ADR-0165-Contract-Registry与插件发布编排.md)。

## 两个唯一真源

- 公共契约版本：`contracts/registry.yaml`。
- 插件版本、依赖和兼容声明：插件自己的 `vastplan.plugin.json`。

不要手工修改 `version.generated.ts`、Go `contractregistry`、生成的 UI Contract Schema、Capability Contract 投影、插件语言包版本、Go 插件运行时 `PluginVersion`、Renderer/Shell 子插件版本文件或部署 Profile 中同一插件的复制版本。它们由发布编排器生成或校验。

## 公共契约升级

修改 Registry 后执行：

```bash
./engineering/tools/platform-dev.sh sync-contracts --write
./engineering/tools/platform-dev.sh sync-contracts
```

`--write` 只更新机械派生文件和 Portal Catalog 的契约范围。插件 Manifest 的兼容声明不会自动扩大；若插件尚未适配新 major，命令会列出阻断插件，必须完成代码适配、测试和 Manifest 声明后再继续。

## 插件升级

1. 在插件 Manifest 中修改 SemVer；这是唯一版本配置点。
2. 从 [release-spec.example.yaml](../../../engineering/deploy/release-spec.example.yaml) 复制 Release Spec，列出本次插件及开发测试目标，并声明变更类别：`implementation`（默认，只变实现）、`additive`（仅新增兼容公开面）或 `breaking`（公开接口破坏）。前两者只构建目标插件；`breaking` 必须把其直接消费者一并列入 Release Spec，避免新接口与旧消费者混合进入候选代。
3. 若本次替换已经运行的插件，开发 Release Spec 可填写该服务当前 Generation 的已验证 `baselineInventory` 文件。生产环境不接受调用方提供的文件；正式发布控制器必须从其可信的活动 Generation Inventory 端口注入同一事实。Plan 会输出目标插件的 `interfaceFingerprint` 和 `interfaceChange`：

   - `implementation` 必须与基线公开接口完全一致；
   - `additive` 必须保留旧接口，并且只新增 map 字段、数组成员或对象字段；
   - 无法读取完整基线、修改或删除既有公开接口时，必须按 `breaking` 处理。

   指纹由已签名 Manifest 的协议、Schema、能力与贡献面计算；版本号、构建路径和包字节变化不会改变它。结构比较只证明公开 JSON 形状的单调性，具体协议的语义兼容性仍由相应 Contract 测试负责：

```bash
./engineering/tools/platform-dev.sh plugin-release plan release.yaml --out /tmp/release-plan.json
```

4. 同步 Registry、Foundation Catalog、Capability Contract、选中插件语言包与 Go Runtime 身份版本、部署精确引用。兼容的公共契约 minor 升级不会仅因 Registry 版本推进而重写 Portal Profile；只有当前 Profile 范围已不接受 canonical 契约、或选中插件的精确引用发生变化时，编排器才重新计算 Profile digest，并同步 Portal Binding 与 Access Profile 的摘要锁：

```bash
./engineering/tools/platform-dev.sh plugin-release prepare release.yaml --out /tmp/release-plan.json
```

5. 本地平台已经 `up` 且测试目标存在时，执行开发候选：

```bash
./engineering/tools/platform-dev.sh plugin-release execute release.yaml --out /tmp/release-plan.json
```

开发执行按依赖顺序构建不可变 `dev.workspace.<digest>` 制品，发布到 local-test/workspace，并提交既有 Backend/Frontend Test Release。候选就绪后由 Service Generation 或 Portal Generation 原子切换；失败不覆盖上一活动代。

开发 Seed Runtime 的实际 Backend Kernel 入口必须与本次完整 Go 依赖闭包构建逐字节一致。dynamic-go 缓存只拥有 ABI Host、`.so` 与相关 Bundle；其中为打包产生的便利 Kernel 副本不得覆盖更新后的 `bin/backend-kernel`。`bootstrap --rebuild-seed` 会在暂存 LKG 前完成该配对和复核，避免出现“插件已更新、实际仍运行旧 Kernel”的混合代。

## 生产边界

将 Release Spec 的 `mode` 改为 `production` 后，`execute` 只生成待审批计划和本地派生配置，不会构建、上传或激活制品。生产候选必须继续经过 remote 仓库、签名与供应链证据、安全准入、异人审批和正式发布控制器。

Release Spec 不允许自定义命令。Runner/Mobile Test Release 未接入前，如果选中含对应入口的插件，编排器会明确失败。
