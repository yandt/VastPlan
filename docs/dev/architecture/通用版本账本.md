# 通用版本账本

本文是 `version.ledger.v1` 的架构真相源。决策理由见 [ADR-0172](../decisions/ADR-0172-通用版本账本与可插拔存储Provider.md)。

## 边界

Version Ledger 保存“内容是什么、父版本是谁、摘要是什么”；领域插件决定“谁能修改、是否批准、何时上线、如何回滚”。它不替代 Artifact Repository、Credentials、Git 平台或业务状态机。

```text
Portal / Deployment / Plugin Settings
              │ version.ledger.v1
              ▼
   Foundation Version Ledger
       ├── File Provider
       ├── Git Provider（后续）
       └── Relational Provider（后续，经 Database Runtime）
```

调用方不能提交 Provider ID。Ledger 根据受信配置中的 `tenant + namespace` 路由选择 Provider 实例；Provider 只接受 Ledger workload，经 Capability Grant Plan 和权限 Enforcer 双重约束。

## 两阶段但不伪造分布式事务

通用写入顺序为：

1. `putVersion` 以 idempotency key 创建不可变版本；重复 key + 相同规范内容返回同一 VersionRef，不同内容冲突。
2. 领域插件以自己的 CAS 提交 VersionRef 和业务状态。
3. 成功后通过可恢复 outbox 执行 `moveHead`，把 Ledger Head 镜像到已提交领域版本。

Head 只用于通用历史入口、导出和 Provider 迁移。领域 CAS 失败时 Head 不动；领域 CAS 成功但 Head 暂未更新时，领域仍是真相源，outbox 可安全重试。未经 Head 或领域引用保护的版本只能在宽限期后、重新复核所有引用后清理。

## 协议对象

- `StreamKey`：namespace + streamId；tenant 永远来自可信 CallContext。
- `VersionRef`：stream、不可变 versionId、sequence 和 contentDigest；不包含文件路径、Git URL 或数据库主键。
- `VersionRecord`：VersionRef、可选 parent、规范 JSON 内容、受限 message/labels、可信 actor 和服务端时间。
- `Head`：stream 下的命名引用和独立 CAS revision。
- `ProviderDescriptor`：协议、版本、一致性、持久性、上限和非敏感配置 Schema。

v1 单个版本内容最大 1 MiB；历史分页最多 200 条；labels 最多 16 项。响应不得包含 Provider endpoint、文件路径、Git 凭证、数据库连接或 Credential material。

### 逻辑版本身份

File、Git、Relational 以及未来其他 Provider 必须共享 `version.identity.v1`，不能各自选择 ID 算法：

```text
versionId = SHA-256(UTF-8(
  "version.identity.v1" NUL
  tenantId              NUL
  namespace             NUL
  streamId              NUL
  idempotencyKey
))
```

结果是 64 位小写十六进制。tenantId 必须是 1–256 字节的无首尾空白有效 UTF-8，所有输入禁止 NUL，其他字段继续遵循线协议 Schema。算法使用宿主提供的 tenantId 原始 UTF-8 字节，不做大小写转换或 Unicode normalization。每个 Provider Descriptor 必须精确声明 `identityAlgorithm: version.identity.v1`，否则不得注册。可信 Ledger 计算 versionId 并放入 Provider Candidate；Provider 使用可信 CallContext 的 tenant 重新派生并比较，随后在同一事务中落实 versionId 唯一约束、幂等约束、sequence 和 createdAt。调用方不能提交 versionId。

versionId 表示一次稳定的逻辑幂等操作，不等于 `contentDigest`：同 key 不同内容仍得到同一个候选 ID，并必须返回冲突；相同内容使用不同 key 可以形成两个审计版本。Git commit、数据库主键和文件 inode 都只是 Provider 内部物理身份。Provider 迁移必须复制原 VersionRecord，禁止重新编号或把物理身份提升为 versionId。字节级向量位于 `contracts/schemas/versioning/v1/testdata/version-identity-vectors.json`，所有异构 SDK 和 Provider 必须通过。

### 内容身份

`contentDigest` 是规范内容字节的 SHA-256 小写十六进制值。可信 Ledger 先拒绝重复 JSON key、非 object 根、超过 64 层/10000 节点/1 MiB 的内容，再把规范内容、统一 versionId 与可信 actor 交给 Provider。Provider 必须在同一个持久化原子边界内分配 sequence、createdAt 并写入记录，Ledger 对返回记录重新计算摘要并核对候选字段。这样 File 单 writer 和未来 Relational 多 writer 使用同一 SPI，不会由协调器在事务外争抢序号。v1 的规范输出使用 UTF-8 紧凑 JSON、按 Unicode 码点顺序递归排列 object key、统一字符串转义，并保留已通过 JSON 校验的数字 token；因此 `1` 与 `1.0` 是两个不同内容，不能依赖语言运行时的浮点转换。

调用方不得自行赋予 `contentDigest`、`versionId`、`actorId` 或 `createdAt`；versionId 由 Ledger 统一派生，actorId 来自 Ledger 对可信 CallContext 的投影，sequence 与 createdAt 由 Provider 原子分配。异构 Provider 不得直接使用语言默认的 `JSON.stringify` 或字典序列化来复算摘要，必须使用对应语言的 Version Ledger SDK 和同一组跨语言 golden vectors；在 SDK 尚未提供前，该语言 Provider 不得声明兼容 `version.ledger.v1`。规范化或身份算法若需改变，必须提升协议版本，不能静默改变既有版本身份。

## Provider 要求

| Provider | 默认一致性 | 适用范围 | 不适用范围 |
|---|---|---|---|
| File | single-writer | 本地开发、Seed、单机恢复 | 多节点并发写 |
| Git | ref-CAS | 审阅、导出、GitOps | 高频在线事务 |
| Relational | linearizable | 企业生产集群、查询和备份 | 数据库尚未配置的 Seed |

File Provider 必须使用私有目录、create-only 内容对象、原子 Root/Head 替换和目录同步；不能把普通共享文件系统自动宣称为集群安全。Git Provider 必须使用精确 commit/ref CAS，禁止 shell 拼接命令和把凭证写入 remote URL。Relational Provider 必须通过 Database Runtime 获取池和事务，使用唯一约束落实 idempotency、versionId 和 Head CAS。

### P1 实现

基础插件位于 `extensions/plugins/cn.vastplan.foundation.versioning.ledger`，使用 leader / leader-owned 拓扑提供 `foundation.versioning.ledger`。这是 File Provider 安全能力的上限：即使未来接入共享 Relational Provider，也不能在未修改拓扑契约和故障矩阵前把当前制品直接配置成 active-active。

受信启动配置注册 Provider instance，并用 namespace 精确路由；公开的 Provider Descriptor 描述实现类型，instance ID 只存在于受信配置，不返回给业务调用方。P1 只允许配置 `version.storage.file.v1`，内存 Provider 只用于同一套契约测试。插件目前不加入 Seed 默认服务，也未替换 Portal 存储；在 P2 出现首个领域消费者时再加入服务组合，避免无消费者的基础服务增加最小启动负担。

File Provider 使用权限 0700 的专用绝对 root；拒绝符号链接、权限过宽的已有目录和文件系统根目录，不会主动 chmod 调用方已有目录。数据位于 `root/tenants/<tenant-hash>/streams/<stream-hash>`，不把 tenant、namespace 或 streamId 明文写进路径。每个版本使用确定性 versionId 文件并通过临时文件 `fsync`、create-only hard link、目录 `fsync` 提交；每个命名 Head 使用临时文件 `fsync`、原子 rename、目录 `fsync` 更新。读取和恢复会复核文件权限、格式版本、规范内容摘要、候选摘要、文件名、stream、sequence 唯一性和完整父链；`.version-*` 崩溃临时文件可忽略，任何已提交文件损坏都 fail-closed。

## Portal 接入边界

Portal Composer 的正式配置进入 `portal.configuration`；测试候选进入 `portal.test.configuration`。Portal Root 保留版本状态、审批人、VersionRef、Release、Test Release 与审计，运行时 Activation 继续携带已经解析的精确 PortalSpec，因此 Ledger 暂时不可用不会令线上页面失去当前配置。

P2 允许当前开发数据直接切换，不设计旧生产数据兼容；但切换必须提供故障注入测试，验证 `putVersion` 成功/Portal CAS 失败、Portal CAS 成功/Head 更新失败、重复请求和 Provider 重启四条恢复路径。
