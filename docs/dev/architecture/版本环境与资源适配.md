# 版本环境与资源适配

本文是 `version.workspace.v1` 与 `version.resource.v1` 的架构真相源。底层不可变账本见[通用版本账本](通用版本账本.md)，决策理由见 [ADR-0173](../decisions/ADR-0173-版本环境与资源适配.md) 与 [ADR-0175](../decisions/ADR-0175-统一版本生命周期与Resource-Adapter能力协商.md)。

## 目标与边界

Version Ledger 是不可变事实存储，不应要求每个启用版本控制的业务功能手工拼装 Ledger API。Version Workspace 在其上提供有 Lease 的编辑会话，Version Resource Adapter 把 Portal 配置、设置、数据库定义、Schema、工作流或文件目录转换成统一快照。调用方只声明“在哪个环境编辑哪个资源”，不能选择 Provider、数据库连接、仓库路径或凭证。Workspace 是显式选择的版本能力，不是所有可编辑资源的隐式存储层；未配置版本控制的领域不得调用它，也不得伪造本地版本历史。

```text
Portal / Settings / Agent / Runner / Workflow
                    │ version.workspace.v1
                    ▼
            Version Workspace Manager
                    │ version.resource.v1
           ┌────────┼─────────┐
      JSON Adapter  Files Adapter  Database Schema Adapter
           └────────┼─────────┘
                    │ version.ledger.v1
                    ▼
            File / Relational / Git Provider
```

Workspace 不接管领域权限、审批、上线和热投影。领域插件仍决定谁能编辑、何时发布和如何生效；Workspace 负责 Session、Lease、基线、变更、commit/discard 和 Head CAS。

## 统一核心协议与能力协商

所有资源共享 Workspace 生命周期，但不强迫实现完全相同的内容功能：

| 层级 | 强制能力 | 可选能力 |
|---|---|---|
| Workspace | describeResource、open/status、read/write、changes、commit/discard/renew、readCommitted | compareCommitted 的详细 diff 取决于 Adapter |
| Resource Adapter | describe、normalize/validate、规范摘要 | diff、materialize、merge |
| 领域插件 | 权限、WorkingCopy/业务 CAS、可见历史元数据 | 审批、发布、恢复、领域语义 |

`describeResource` 通过受信 Environment Binding 返回精确 Environment digest、contentKind、选定/允许 mode、有效大小上限、秘密策略和能力位；不返回 Provider、endpoint、路径、AdapterConfig 或凭证。调用方和 Workbench 以能力位决定是否显示 diff、merge、物化等操作，不先调用再猜测。

摘要比较属于核心能力：任何规范 Snapshot 都可以判断是否变化。详细 diff 属于 Adapter 能力；不支持时 `changes/compareCommitted` 必须明确返回 `diffAvailable=false`，但 `dirty` 仍由左右摘要决定。当前 `ChangesResult` 把 dirty 强绑定到 summary.total，P2.2.2 将解除该约束，避免 Blob Adapter 伪造差异。

### 任意内容的统一表达

Wire 保持 `json / files` 两个最小内容形态：

- 最大 1 MiB 的结构化配置、规则和 Schema 使用规范 JSON object；
- 纯文本、脚本、图片、PDF、模型、压缩包和目录统一使用排序 Files Manifest；
- 单文本或单二进制就是只有一个 FileEntry 的清单，不为每种 MIME 扩展 Snapshot union；
- Ledger 保存清单、摘要和版本关系，实际字节进入受信 Object/Artifact Store；
- 超大数据集只保存外部不可变引用，不把数据块逐个写入版本账本。

标准 Adapter 预计为 `version.resource.json.v1 / text.v1 / blob.v1 / files.v1`。Text、Blob、Files 都投影为 `ContentFiles`，区别在编码规范、安全校验、diff 和物化能力。业务插件优先复用这些 Adapter；只有数据库 Schema 等领域语义确有差异时才新增 Adapter。

文件扩展名和 mediaType 只是声明。Files/Blob Adapter 仍须复核对象摘要、大小、允许类型、路径穿越、符号链接、压缩炸弹与安全扫描结论；密码、token、私钥和其他 material 不能因为进入二进制对象而绕过 CredentialRef 规则。

Files 内容采用两阶段暂存，不把字节放进 `writeSnapshot`：

1. 可信 Workspace/Content Store 为 tenant、resource、预期 digest/size 签发短时上传 Lease；
2. 调用方通过专用流式数据面上传，Store 边写边复核上限和摘要，并执行所需安全准入；
3. 上传完成后返回不透明内容引用，Adapter 只接受当前 tenant 可访问且已完成的对象；
4. `writeSnapshot` 仅提交排序 Manifest，commit 后由版本引用保护对象；未提交暂存对象在 Lease/宽限期后回收。

上传 URL、对象物理路径、存储 Provider 与凭据不进入 Snapshot、Session 或历史。Content Staging 留在 P2.4；JSON P2.3 不依赖该数据面。

## 三档运行模式

| 模式 | 默认用途 | 物理形态 | 创建成本 |
|---|---|---|---|
| `snapshot` | JSON 配置、设置、规则、工作流 | 内存快照 | 最低，默认 |
| `overlay` | 脚本、模板、多文件配置 | 内容寻址基线 + 写时复制 Overlay | 与变更量相关 |
| `git` | GitOps、代码审阅、远端同步 | 真实 Git repository/worktree | 最高，显式启用 |

JSON Adapter 从协议上禁止声明 Git 模式。Workspace Manager 不得为每个 Session 或插件启动进程；每个服务宿主共享 Manager，只有 Adapter 的原生库冲突、第三方隔离或企业策略要求时才使用独立进程。Overlay 必须懒物化，只保存变化文件；Git 不得成为 Portal、Settings 等在线事务的隐式默认值。

## 可信 Environment Profile

Environment Profile 由部署配置或在线平台配置提供，例如：

```json
{
  "protocol": "version.resource.v1",
  "id": "platform-development",
  "revision": 1,
  "bindings": [
    {
      "resourceType": "portal.configuration",
      "namespace": "portal.configuration",
      "adapter": "version.resource.json.v1",
      "allowedModes": ["snapshot"],
      "defaultMode": "snapshot",
      "projectionPolicy": "domain-hot"
    },
    {
      "resourceType": "script.bundle",
      "namespace": "script.bundle",
      "adapter": "version.resource.files.v1",
      "allowedModes": ["overlay", "git"],
      "defaultMode": "overlay",
      "projectionPolicy": "none"
    }
  ],
  "limits": {
    "maxSessionsPerTenant": 64,
    "maxLeaseSeconds": 3600,
    "maxSnapshotBytes": 1048576,
    "maxOverlayBytes": 67108864
  }
}
```

绑定中没有 Provider、endpoint、数据库连接或 CredentialRef。namespace 到存储 Provider 的路由继续由 Version Ledger 的受信配置决定。Catalog 按 `id + digest` 保留已加载的 Profile 修订，并把同 ID 的最高 revision 用于新会话；Session 和已提交版本读取都必须绑定精确 digest。Profile 改变后，既有 Session 与历史 VersionRef 不得静默继承新权限或 Adapter 配置；所需 digest 未加载时失败关闭，不能退回当前修订。

Environment digest 使用 Version Ledger 的同一套规范 JSON object 规则计算 SHA-256；Snapshot JSON 也必须是最大 1 MiB 的 object。文件资源只把确定性排序的路径、摘要、大小和 mode 清单写入 Ledger，实际文件总量受 Overlay 配额约束，文件字节不受 JSON 快照上限误伤。

## Session 工作流

1. `open` 根据 Environment Profile 解析 Resource Binding、模式、基线 Ref 和 Head revision，生成不可伪造的 Session ID 与 Lease。
2. `readSnapshot` 返回规范 JSON 或内容寻址文件清单；文件字节仍在对象/制品存储。
3. `writeSnapshot` 使用 Session revision CAS，Adapter 校验、规范化并计算摘要；写操作只改变隔离 Session。
4. `changes` 返回确定性排序的变化路径与统计，不在普通列表页面主动计算大型 diff。
5. `commit` 先以可信领域持久化并传入的稳定 `operationId` 写 Ledger，再以打开时捕获的 Head revision 执行 CAS；成功后 Session 进入 `Committed`。同一领域操作在 Session 丢失并重开后仍复用同一逻辑 VersionRef。
6. `discard` 丢弃候选；`renew` 只能在配额和 Profile 上限内延长 Lease；超时 Session 进入 `Expired` 并清理 Overlay。

只读 Session 不能绑定待更新 Head。Session ID、Lease、Environment digest、tenant、资源标识和 actor 均由可信宿主投影或生成，不进入任意业务 metadata。

## 在线热投影与性能

领域热路径不能批量装配历史版本。以 Portal 为例，P2.3 按 [Portal 可选版本控制接入](Portal可选版本控制接入.md) 分为两条路径：

- 未配置 Workspace 时只保存 WorkingCopy、冻结 Publication 与 Release，不生成 VersionRef、Head 或通用历史；
- 配置 Workspace 后才保存领域 CAS 已确认版本的轻量元数据和 VersionRef；
- 两种模式都保存当前 WorkingCopy、当前 Publication、当前 Release 与物化 PortalSpec 的完整有界热投影；
- Portal 列表、当前 WorkingCopy 和线上 Runtime 不访问 Ledger；
- 历史详情按需读取，精确 VersionRef 可进入有界进程内缓存；不可变内容无需失效广播；
- 普通保存不写 Ledger；只有启用版本控制并提交 Publication 时才创建 detached VersionRef，再由领域 CAS 确认，P2.3 不提前移动 Head。

File Provider 仍只用于开发和 Seed。生产 active-active 写入必须由 Relational Provider 使用事务、唯一约束和 Head CAS；Git Provider 只适合明确的 GitOps 路由。

## 数据库资源接入

数据库作为 Ledger 存储时使用 `version.storage.relational.v1`，调用方完全无感。数据库定义或 Schema 作为被版本化资源时使用独立 Adapter：

- `version.resource.database-connection.v1` 保存非敏感连接定义、池参数和 CredentialRef，绝不保存 material；
- `version.resource.database-schema.v1` 把实际 Schema 规范化为 JSON，diff 生成数据库无关迁移意图；
- PostgreSQL、MySQL、SQL Server、SQLite 等方言 Adapter 把迁移意图编译为候选 SQL；审批和执行仍由数据库领域插件经 Database Runtime 完成；
- 订单、支付、日志、指标、消息和高频库存不逐条进入 Workspace，继续使用事务数据库、CDC、审计表和备份。

Database Runtime 持有连接池和 Material Lease。Workspace 与 Adapter 只能获得数据库领域插件提供的窄能力，不能取得明文凭证或直接拼接远端连接。

## 语言与运行方式

Workspace Manager 首选 Go：现有 Capability Bus、CallContext、Version Ledger 和 Shared State 均有 Go 契约，Session 并发、Lease、文件原子性和低常驻资源最合适。Snapshot JSON Adapter 同样优先 Go。

Git/File Adapter 实施前重新比较 Go、Rust 和 libgit2 生态；数据库 Schema Adapter 按驱动与方言生态选择 Go、Rust、Java、C# 或其他语言，不为统一语言牺牲成熟度。Python、Node 和其他语言消费者通过相同 Wire 协议和各语言 SDK 使用 Workspace，不在本地重新实现版本规则。

- P2.2.1：`commit.operationId` 可跨 Session 重试；`readCommitted/compareCommitted` 按精确 Environment digest 经同一 Adapter 读取和比较已提交 VersionRef；Catalog 保留同 ID 多修订并只把最高 revision 用于新会话；

- 契约测试覆盖跨 Session 幂等重试、历史环境精确解析、能力声明/实现一致性、无 diff 资源的摘要变化、已提交版本读取/比较、Head 冲突、Lease/配额、actor 隔离、只读会话、陈旧 revision、秘密拒绝和丢失响应恢复。

当前 Session 不做生产级持久化或跨 Leader 恢复。这是明确的临时编辑边界，不是遗漏的事实存储：已提交事实由 Ledger 恢复，未提交候选由调用方重开。P2.3 只在 Portal 显式启用版本控制时接入 Workspace；未配置时 Portal 仍是无历史的普通 WorkingCopy。P2.2.1/P2.2.2 已完成，下一步进入 P2.3a 的 Portal 无版本路径领域整理。P2.4/P2.5 再引入 Text/Blob/Files、Overlay、Git 和额外语言 SDK。
