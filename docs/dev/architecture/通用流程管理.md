# 通用流程管理

本文是 VastPlan 通用流程管理插件、功能点注册、流程定义、运行实例与领域动作边界的单一真相源。架构取舍见 [ADR-0205](../decisions/ADR-0205-流程管理插件与领域动作边界.md)。

## 1. 目标与非目标

流程管理把 Portal 发布等功能的“冻结候选之后、最终生效之前”的中间过程集中管理，并允许每个服务绑定自己的流程定义。

目标：

- 功能插件以签名声明注册可纳管资源和有限动作；
- 服务管理员在线创建、发布和绑定不可变流程修订；
- 人工任务、领域动作、恢复、幂等和审计由一个插件统一负责；
- 领域插件无需理解流程拓扑或调用 `start`，只声明准备入口、资源契约和 execute/compensate 动作；
- 未安装或未选择流程插件的服务不暴露流程管理能力。

非目标：

- 不提供任意脚本、任意 HTTP Webhook 或表达式执行器；
- 不取代 Authorization、Approval Policy 或最终领域系统；
- 不把资源正文复制进流程实例，也不把流程插件建设成任意业务数据库；
- 不使用图谱或代码关系图作为运行时依赖。

## 2. 插件边界

`cn.vastplan.platform.workflow.orchestrator` 是独立全栈平台插件。

| 所有者 | 持有内容 | 不持有内容 |
|---|---|---|
| Governed Resource Store（目标态） | WorkingCopy、Candidate、不可变修订、Digest、资源 CAS 与审计 | 流程游标、最终生效事实 |
| 流程插件 | Definition Revision、Binding、Instance、Task、Token、Audit | 资源正文、最终生效事实 |
| 功能插件 | 资源 Schema、校验规则、准备入口、允许动作 | Repository、流程拓扑、流程状态 |
| 最终领域系统 | 用户账户、Portal Activation、部署结果等生效事实 | 流程定义、流程任务 |
| Approval Policy | 对精确资源与摘要给出审批策略决定 | 流程实例、发布状态、角色存储 |
| Authorization | 当前调用者是否具备操作权限 | 业务审批结论、流程推进结论 |

编排器与通用资源服务后端使用 Go、`trusted-process`、`active-active`、`queue`，耐久状态使用 `foundation.data.record-store`。前端默认使用 TypeScript Workbench，并通过受治理页面 Provider 机制允许替换 UI，而不替换后端协议和状态。

## 3. 功能点注册

功能插件在签名 Manifest 中声明 `contributes.backend.workflowFeatures`：

```json
{
  "id": "platform.portal.publication",
  "contract": "1.0.0",
  "resourceKind": "portal.publication",
  "digestRequired": true,
  "prepare": {
    "capability": "platform.portal-composer",
    "operation": "preparePublication"
  },
  "unboundPolicy": "direct",
  "unboundActionId": "portal.release",
  "actions": [
    {
      "id": "portal.release",
      "capability": "platform.portal-composer",
      "operation": "executePublicationRelease",
      "permission": "platform.portal.publish",
      "terminal": true,
      "compensatable": false
    }
  ]
}
```

`unboundPolicy` 明确功能点尚未绑定流程时的行为：`deny`（默认）拒绝启动，`direct` 通过 `unboundActionId` 指定的终态动作直通。直通不是领域插件捕获“绑定不存在”后的降级分支；流程插件仍创建 `mode=direct` 的耐久实例、动作工作项和审计记录，再按签名目录调用领域动作。这样“管理员允许直通”与“配置遗漏”可被区分，动作失败也会进入 `suspended` 而不是被误报为成功。

注册表来自已验签的 Contribution Inventory，Owner 固定为贡献插件。`prepare` 与动作目标都来自签名目录；请求不能覆盖 capability、operation、插件 ID 或 URL。流程定义只保存 `featureId` 和 `actionId`，发布时锁定兼容目录摘要。

`workflowFeatures` 是声明式贡献，不进入 Plugin Host 运行时 Contribution Bus。缺少功能点、Owner 变化、动作删除或契约范围不兼容时，新绑定失败；已运行实例保持原定义但在调用前仍必须解析兼容动作，否则安全暂停并等待管理员处理。

## 4. 协议

### 4.1 `governed.operation.v1`

所有入口统一调用 Governed Operation Gateway，而不是由功能插件或前端拼接两次调用。Gateway：

1. 按签名功能目录调用准备操作；
2. 验证返回的标准 `GovernedResource { kind, id, digest, revision }`；
3. 在同一幂等身份下交给已选择的编排 Provider；
4. 返回 `pending | completed | rejected | suspended` 的中立治理结果。

准备成功但编排暂时不可达时必须失败关闭，并由耐久恢复任务继续提交；不能因为 Hook 或 Provider 不可达而直接执行终态动作。现有 `hook` 仍只用于限流、计量和通知。

### 4.2 `workflow.orchestration.v1`

管理面与任务面统一使用一个能力协议，至少包含：

- `publishDefinition`：校验并发布新的连续不可变修订；
- `bindDefinition`：将服务与功能点绑定精确定义修订；
- `start`：Gateway 内部为冻结资源和摘要幂等创建实例；不作为业务插件集成 API；
- `getInstance`、`listTasks`：读取运行态与当前主体任务；
- `completeTask`：以 task revision CAS 完成人工任务；
- `completeAction`：提交领域动作执行结果并推进；
- `cancel`：按策略终止未完成实例。

身份只来自可信 `CallContext`。请求体不得携带 tenant、actor、roles 或授权结论。

### 4.3 `workflow.action.v1`

流程插件调用功能所有者时使用封闭动作信封：

```text
ActionRequest {
  instanceId, definitionRevision, featureId, actionId,
  resourceRef, resourceDigest, attempt, idempotencyKey
}
```

领域动作分三类：

- `prepare`：只验证精确候选、摘要和前置条件，可返回短期 prepare token；
- `execute`：以幂等键执行领域 CAS；成功后返回领域事实引用；
- `compensate`：仅当动作声明 `compensatable=true` 时可调用，且不能伪造“撤销”不可逆发布。

动作所有者必须重新校验资源身份、摘要、当前状态、权限委托和幂等键。编排器的“节点已通过”不是领域授权。

## 5. 三层节点模型

定义由 `entryNodeId`、节点和有向边组成。节点 ID 在修订内唯一，所有可达路径必须终止，边不得引用不存在节点。定义内容计算 SHA-256；`(tenant, definitionId, revision)` 唯一且修订必须从 1 连续递增。

### 5.1 内核节点

内核节点定义流程执行 IR，拥有统一的持久化、恢复和令牌语义：

- `workflow.core.manual-task`：创建人工任务；
- `workflow.core.action`：解析并执行功能点签名动作；
- `workflow.core.decision`：对受治理的类型化事实求值；
- `workflow.core.timer`、`workflow.core.event-wait`：创建耐久等待；
- `workflow.core.fork`、`workflow.core.join`：管理并行执行令牌；
- `workflow.core.subflow`：固定引用精确子流程修订；
- `workflow.core.end`：以终态结束实例。

首个实现里只有 `manual-task`、`action` 和 `end` 可发布；其他内核节点必须在调度、唤醒、取消和恢复测试完成后逐项启用。

### 5.2 Node Template

外部插件通过签名 `contributes.backend.workflowNodeTemplates` 提供节点模板、配置 JSON Schema、输入/输出契约和展开版本。发布流程定义时，编译器把模板展开为内核 IR，校验完整拓扑并记录模板 Artifact Ref、模板描述符摘要、编译器版本、展开后 IR 摘要和源映射。

实例只执行锁定的 IR，不在运行时调用模板插件。邮件确认、电话确认、通知加等待、限次重试等优先使用模板。

### 5.3 Node Provider

只有不能由内核节点组合表达的行为才使用 `contributes.backend.workflowNodeProviders`。Provider 接收锁定配置、最小输入事实和当前信号，返回受限效果：

```text
Complete(outcome, facts)
Wait(eventContract, correlation, deadline)
RetryAfter(at, reason)
Fail(code)
```

Provider 不接收 Repository、Instance 写端口或任意调用目标。编排器校验输出契约并以 CAS 持久化效果。定义发布时锁定 Provider 插件版本、制品摘要和契约版本；活跃实例引用存在时禁止卸载对应制品。Provider 缺失或违约时实例进入 `suspended`，不得静默换实现。

一个物理插件可以贡献多个具有相同发布、凭证与故障边界的模板或 Provider。纯逻辑节点应交付为签名模板 Bundle，不为每个节点启动独立进程。

## 6. 运行与恢复

1. 调用方调用 Governed Operation Gateway；Gateway 调用功能点准备操作并取得标准冻结资源。目标态由 Governed Resource Store 持久化该资源，迁移期允许功能插件的兼容准备适配器持有候选。
2. Gateway 内部调用 `start`；流程插件读取服务绑定并固定精确 Definition Revision，或按签名策略选择直通。
3. 执行器从 entry 开始推进，遇到人工节点创建一个待办，遇到动作节点创建一个待执行动作。
4. 人工完成或动作结果以 Instance revision CAS 写入，再继续推进。
5. 到达终点后记录终态；只有领域 terminal action 成功，领域对象才可视为已发布。

每个变更同时写入结构化 Audit Event。进程重启后按非终态实例扫描恢复；局部通知只负责降低延迟，Record Store 始终是恢复真相源。动作调用使用稳定幂等键 `instance/node/attempt`，超时只能重试同一键。

## 7. Portal 接入

Portal 是首个功能点：

```text
WorkingCopy -> Frozen Publication Candidate -> Workflow Instance
                                             -> portal.release action
                                             -> immutable Portal Release
```

迁移期保留旧接口作为未选择流程插件时的直通兼容路径。选择流程插件后，Portal 页面只调用注入的提交端口，组合入口把它绑定到 `/govern`；页面和 Portal Composer 都不查询 Binding，也不调用 `start`。当前准备适配器仍复用 Portal Repository 冻结 Publication Candidate，执行 `portal.release` 时重新读取 Candidate、验证 digest 和当前状态，并以 CAS 生成 Release。迁移到 Governed Resource Store 后，兼容 Publication 状态降为读模型。

流程定义可按服务包含任意数量的人工节点，或直接进入发布动作。审批策略节点由流程插件调用 `approval.policy.v2`，但 Authorization 仍在每次用户任务和领域动作调用时执行。

## 8. 安全与治理

- Manifest schema 拒绝未知动作字段、非法权限名、非 workload 动作和任意目标覆盖。
- Node Template 只能展开为受支持内核节点；Node Provider 只能返回受限效果，不能直接推进实例。
- UI 只能提交 Workbench 定义和协议数据，不能注入 React 节点、函数或脚本。
- 流程发布、绑定、任务处理和实例取消使用独立权限；服务管理员只能管理授权服务范围。
- 管理 API 的服务身份只取自可信 `ManagementTarget`；绑定、实例、任务列表以及任务完成和实例取消都按该服务身份隔离，浏览器请求不能覆盖它。
- 运行实例不保存领域正文，只保存引用、摘要和最小审计投影。
- 日志与审计不得记录候选正文、凭证或审批秘密。

## 9. 演进与测试

每次数据格式升级必须提供连续 `vN -> vN+1` 迁移和夹具测试。协议使用 additive minor 演进；删除节点类型、效果语义、动作语义或状态值必须提升 major。测试至少覆盖：定义校验、模板展开确定性、恶意模板拒绝、Provider 输出校验、Provider 升级锁定、修订连续性、绑定 CAS、启动幂等、任务并发完成、动作重试、等待唤醒、防重放、重启恢复、摘要变化拒绝、权限撤销和最终领域 CAS。

## 10. 当前交付边界

本次首个纵向切片已经交付：签名功能点/模板/Provider 契约、可信目录装配、不可变定义与服务绑定、`manual-task/action/end` 三个内核节点、直通与人工流程、任务/实例管理 API、默认可替换 Workbench UI，以及 Portal 发布的可选 `/govern` 接入。`start` 只保留为编排器内部方法，浏览器不能提交服务身份。

尚未宣称完成的目标态能力包括：通用 Governed Resource Store、模板到内核 IR 的编译器、受限 Node Provider 运行时、定时器/事件/并行/子流程内核节点，以及旧 Portal Publication 状态向通用资源修订的迁移。当前发布器会拒绝包含这些尚未启用节点的定义，不能把目录可见误认为运行时已支持。
