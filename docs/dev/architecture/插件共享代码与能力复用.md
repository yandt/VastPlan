# 插件共享代码与能力复用

> 本文是 Backend/Desktop/Mobile/Portal 插件共享协议、SDK、公共 Library 和运行能力的单一真相源。架构取舍见 [ADR-0150](../decisions/ADR-0150-插件共享代码与能力复用边界.md)。

## 1. 四类复用

| 类型 | 目录/交付 | 可以包含 | 禁止包含 |
|---|---|---|---|
| Contracts | `contracts/proto`、`contracts/schemas`、`contracts/generated/<language>` | wire 类型、Schema、错误/协议标识、兼容规则 | 存储、网络客户端、重试事务、宿主可信状态 |
| SDK | `extensions/sdk/<language>` | 插件生命周期、HostCall、窄上下文视图、配置/状态/凭证客户端、安全默认值 | 内核实现、具体插件业务、共享可变状态 |
| Library | `extensions/libraries/<language>/<name>` | 无权限、确定性、可独立测试的纯算法 | HostCall、凭证读取、全局单例、后台进程、业务存储 |
| Provider/Service 插件 | `extensions/plugins/<id>` | 可替换实现、状态、连接、凭证、集群和外部系统适配 | 被其他插件源码导入、绕过 capability 寻址 |

`core/internal` 只承载可信宿主和内核实现。`extensions/plugins`、`extensions/sdk` 与 `extensions/libraries` 都不得依赖它。

## 2. 选择规则

- 高频、细粒度、无状态计算使用 Library；
- 与插件协议会话直接相关的客户端逻辑使用 SDK；
- 需要动态替换、在线配置、跨语言、独立隔离、状态、凭证或集群化时使用 Provider/Service 插件；
- 插件启动前必须存在的协议、类型和兼容规则必须属于 Contracts，不能做成普通插件；
- 插件之间只能经 capability/protocol 交互，不能依赖插件 ID、文件路径或实现包。

独立插件还必须拥有真实的交付或运行边界：独立替换/版本、在线配置、状态或凭证、外部系统适配、故障隔离、集群生命周期、内容寻址按需下载中至少一项。逻辑贡献不等于物理进程；同一信任域内的多个高频无状态规则，应优先作为一个 Provider 内部的独立模块或签名数据 Bundle。测试与示例插件不进入生产 Foundation 插件目录。完整门禁见 [ADR-0152](../decisions/ADR-0152-插件边界门禁与权限策略物理收敛.md)。

同一 capability 可以绑定本节点 Provider 或远端集群 Service。调用方始终经内核寻址，并使用相同的 deadline、取消、身份投影、授权和错误契约。

## 3. 多语言交付

### Go

Contracts、SDK 和 Library 以独立模块语义维护，发布构建静态链接到插件二进制。插件制品自包含，不依赖目标服务器 Go module cache 或系统动态库。公开依赖变化会改变插件字节，必须形成新插件版本。

### Node

业务依赖默认打入插件 bundle。只有 Runtime Profile 明确列出的官方 SDK 可 externalize，并由共享 Node Runtime 绑定精确兼容版本；普通 npm 包不能从目标服务器在线漂移解析，也不能污染共享全局状态。

### Python

基础 SDK/Protobuf 可由可信 Runtime 提供。业务依赖使用带摘要的锁和离线 wheel；共享环境按 Runtime、发布者信任域、隔离等级和依赖锁摘要分池，不在不兼容插件之间复用可变 `site-packages`。

### dynamic-go

只用于策略批准的第一方插件。模块必须匹配当前 Host ABI 指纹；候选和活动代使用不同 Host Generation。它提供进程内调用效率，但不承担普通公共 Library 的发布和解析。

## 4. 版本与制品

每个插件构建记录以下依赖闭包：

```text
plugin source
+ imported Contracts
+ imported SDK packages
+ imported Libraries
+ language lock
+ builder/toolchain identity
= plugin build digest
```

SBOM 必须同时记录静态依赖和 Runtime 提供依赖。stable 精确引用继续不可覆盖；开发快速循环使用内容寻址的 `workspace`，完整测试使用唯一 `dev.*` 预发布版本。

版本传播规则：

- 内核内部实现变化：插件不重建；
- Contracts 兼容增加：只重建实际使用该契约且需要新能力的插件；
- Go SDK/Library 实现变化：实际链接的插件提升 patch，破坏性 API 变化同时提升 SDK major；
- Provider/Service 实现变化但协议兼容：消费者不重建；
- capability protocol major 变化：通过依赖解析选择兼容 Provider，禁止运行时猜测或静默降级。

## 5. 工程门禁

架构测试和发布构建必须共同验证：

1. 插件及其传递依赖中不存在 `core/**`；
2. SDK 不依赖 `core/**` 或具体插件；
3. 插件不导入其他插件实现；
4. Library 不调用 Host、读取凭证、启动后台进程或持有共享可变状态；
5. capability 调用经过可信 CallContext 投影和授权；
6. 构建摘要只包含实际依赖，不能因无关内核或插件变化全量失效；
7. 制品 SBOM、清单依赖约束与真实编译/运行依赖一致。

## 6. 当前实施状态

已完成：

1. Protobuf Go 生成物进入 `contracts/generated/go`；
2. 协议常量、错误码、资源限制、扩展点、只读 Context View、Runtime Audience 和 dynamic-go ABI 进入 `contracts/runtime/go`；
3. 可信 CallContext 和 RuntimeIdentity 进入 `core/internal`；
4. 签名制品仓库、供应链、配置、Shared State 等公开复用代码进入 `extensions/libraries/go`；
5. Repository 插件不再依赖 Backend `pluginservice`，普通插件和 Go SDK 对 `core/**` 的直接导入均为零；
6. 架构门禁拒绝插件/SDK/Library 新增任何内核实现依赖；
7. Platform Dev 按每个 Go 二进制的真实依赖闭包计算独立缓存摘要；
8. Platform Dev 只装配 Backend Seed Profile、Portal Platform Catalog 与 Manifest 依赖闭包所需制品，普通开发插件统一进入 `workspace/testing` 发布链路。
