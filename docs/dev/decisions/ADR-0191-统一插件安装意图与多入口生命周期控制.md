# ADR-0191 统一插件安装意图与多入口生命周期控制

- 状态：已采纳，P0—P7 已实施
- 日期：2026-08-02
- 关联：[ADR-0142](ADR-0142-内核启动与业务发布完全分离.md)、[ADR-0143](ADR-0143-插件化应用意图规划与派生依赖.md)、[ADR-0144](ADR-0144-组合服务代际热升级与插件动态调试.md)、[ADR-0147](ADR-0147-种子与在线服务配置统一发布机制.md)、[ADR-0148](ADR-0148-公共服务基线与种子配置分域.md)、[ADR-0180](ADR-0180-Catalog驱动的统一插件自发现与本地插件库.md)

## 背景

系统需要同时支持三种入口：平台服务控制器跨服务管理插件、服务自身在有权限时浏览市场并安装插件、开发环境在源码或本地库变化后自动安装生效。如果三者分别实现下载、依赖解析、审批和发布，将产生三套版本选择、安全校验、回滚和审计语义，开发态也可能绕过生产候选执行链。

现有系统已经拥有 Local Plugin Library/Catalog、Artifact Repository Resolver、Application Intent、Composition Planner、Deployment Manager、内核 Preview/Publish、Node Agent Generation 和 Test Release。缺口不是新的安装器，而是位于这些能力之上的统一安装意图协议和多入口策略。

## 决策

### 1. 一个安装意图，三个受信来源

定义 `PluginInstallationIntent`/Preview 协议，来源只有：

- `controller`：平台服务控制器可管理租户内获授权的逻辑服务；
- `self-service`：服务自身市场入口，目标 deployment 必须由可信 Portal 管理绑定派生；
- `development`：开发控制器只面向显式绑定的开发服务。

来源不进入浏览器可写请求。组合根按受治理 operation 选择一次来源协议，构造固定 `Source` 策略对象后注入共享工作流；后续层不再读取环境字符串、布尔开关或自行猜测入口。服务自助 operation 只允许可信 Portal BFF 调用，P4 的 BFF 必须从 `ManagementTarget` 派生目标而不是转发浏览器目标字段。

### 2. 契约独立，实现暂时内聚

安装契约位于中立 Go Library，执行模块首版放入现有 Deployment Manager：

- Artifact Repository 继续只负责目录、签名事实、SemVer 求解和精确 Artifact Lock；
- Composition Planner 继续只负责依赖闭包、配置计划、Provider Binding 和运行提案；
- Deployment Manager 把安装变化投影到 Application Intent，持有候选、审批、发布和回滚工作流；
- Kernel/Controller/Node Agent 保持不变，只消费既有 Deployment/Assignment 精确锁。

当安装控制器出现独立扩缩容、故障域或发布生命周期需求时，可按相同协议从 Deployment Manager 拆出；当前不新增空壳插件或常驻进程。

### 3. 服务是目标，节点不是目标

安装目标使用 `kernel + deployment + unitId`。控制器生成一个逻辑服务修订，由既有 Scheduler 和 Node Agent 根据副本、放置与更新策略滚动到节点。普通入口不得直接向某一物理节点安装插件；节点级操作只允许诊断或灾难恢复流程。

### 4. 预览无副作用并绑定全部漂移输入

预览按以下顺序执行：

1. 读取当前活动 Application Intent；
2. 只修改指定 service 的一个根应用插件要求；
3. 调用既有 Planner；
4. 获得传递依赖、配置缺口、Provider Binding、精确 Artifact Lock 与 Catalog revision；
5. 调用既有内核 Preview 复验 Platform Profile 和最终 Deployment；
6. 返回新增、升级、删除的完整包差异与 `planDigest`，不写修订、不保护引用、不激活制品。

后续提交必须重新绑定活动 revision、候选 Intent digest、planDigest、Platform Profile、Catalog revision、Artifact Lock 和内核 Preview digest。任一输入变化都使候选 stale，不能继续沿用原审批。

### 5. 只允许应用插件成为用户根选择

服务控制器和服务自助入口只能选择固有管理分类为 `application` 的插件。Foundation/Platform 只能通过 Platform Profile；Library/Runtime 只能由依赖或平台 Provider 选择。开发来源可在显式开发模式下选择 `development` 分类，但不能把该结果晋级为稳定生产证明。

### 6. 权限和审批分开

市场浏览、安装预览、申请、审批、激活、卸载和回滚使用独立权限。权限回答“主体是否可以执行动作”，审批策略回答“本次变更是否需要额外批准”。第一方低风险插件可以由企业策略允许直接激活；第三方、敏感 capability、Runtime 或平台级变更默认要求审批。服务自助即使拥有预览权限，也不能越过宿主绑定管理其他服务。

P1 新增 `platform.deployment.plugin.preview`，只授予只读安装预览。后续写操作不得复用该权限。

### 7. 开发自动安装不建立旁路

开发目录或 Local Plugin Library 变化只产生一个 `development` Installation Intent：

- 必须存在显式 plugin/service 绑定；
- 只允许受信 `platform-dev` 系统调用和开发模式上下文；
- 可以按开发策略免人工审批，但仍执行 Manifest、依赖、UI Contract、精确摘要和目标兼容校验；
- 最终仍进入完整 Service Generation/Portal Generation 候选、readiness 和自动回滚；
- 不自动把所有新插件安装到所有开发服务。

### 8. Seed 在线管理与恢复边界

首次引导后，Seed 服务的应用插件也可通过相同在线安装意图管理；本地 Seed 文件只保留 Recovery Baseline、信任根、内核和恢复所需最小插件。普通 `up/restart` 仅恢复最后提交状态，不解析市场候选、不构建、不发布。该决定收窄 ADR-0148 中“Seed Service 配置只能本地管理”的长期范围，但不取消其灾难恢复本地真源。

### 9. 全栈插件使用一个候选 Saga

Backend、Portal、Desktop 或 Mobile 贡献属于同一全栈插件时，安装意图只创建一个候选；各内核 Adapter 生成自己的运行产物，所有候选准备完成后再切换。不能出现后端已激活、前端仍为旧版本的长期混合状态；失败时执行补偿回滚而不是分布式 ACID 假设。

## 语言与运行方式

- 后端首版使用 Go 并作为 Deployment Manager 内部工作流模块运行，可直接复用现有 DTO、CAS、NATS 调用、Planner 和状态恢复；Node.js/Python 不改善该低频确定性控制路径。
- Portal 市场和安装页面使用 TypeScript/React + Workbench，只提交数据驱动意图。
- 开发监听继续使用现有 Go `platform-dev` 工具；各语言插件的构建仍交给对应 Runtime/Builder。
- 本阶段不新增进程；运行方式与未来是否拆出控制器独立决策。

## 备选方案

### 三套入口分别实现

首期看似简单，但必然形成不同权限、校验、版本选择和回滚语义；拒绝。

### 立即新建独立安装控制器插件

边界清楚，但当前没有独立状态、凭证、外部系统或故障隔离收益，会增加进程和分布式事务；暂缓。

### 把市场和自动安装放入内核

会把业务工作流、Repository 来源、开发文件监听和审批带入封板内核，也破坏启动/发布分离；拒绝。

## 实施阶段

1. P0：固定本文、权威架构、权限分层和语言选择；
2. P1：定义统一 Preview 契约，在 Deployment Manager 中实现只读安装/升级/卸载预览和来源范围强制；
3. P2：持久化 Installation Candidate，接入提交、审批、激活、取消和回滚；（已完成）
4. P3：服务控制器增加跨服务插件页，支持批量目标和滚动进度；（已完成）
5. P4：服务自身增加硬绑定范围的市场页和可配置审批策略；
6. P5：开发目录/Catalog watch 生成自动候选并接入现有 Generation；（已完成）
7. P6：完成 Portal/Backend 全栈候选 Saga、Seed 在线交接和真实多节点 E2E。（控制链与补偿测试已完成）
8. P7：把 DataModel 迁移影响、审批/备份证据和候选路由前 Schema Controller 执行纳入同一安装 Saga。（已完成，见 ADR-0195）

## 实施记录

- 2026-08-02：P0—P1 完成。新增 `extensions/libraries/go/plugininstallation` 中立协议；三个受治理 operation 在入口固定 `controller/self-service/development` 策略后进入同一工作流，不滥用会被受众投影裁剪的 `CallContext.metadata`。Deployment Manager 0.22.0 把一个应用根插件安装、升级或卸载投影为候选 Application Intent，复用 Planner、Catalog Artifact Lock 与 Kernel Preview，并返回精确包差异、配置缺口、Generation 影响及审批提示。预览不写 Shared State；服务自助入口先要求可信 Portal BFF，P4 再接入 ManagementTarget 派生；开发免审批只允许受信 `platform-dev` 系统调用且 P1 必须命中现有 TestTargetBinding，新增插件的开发绑定随 P5 实现。测试覆盖无副作用、Catalog/Preview 摘要绑定、入口身份拒绝、开发目标绑定和 Platform 插件拒绝。
- 2026-08-02：P2 完成。Deployment Manager 0.23.0 在同一租户 Shared State 中持久化 Installation Candidate，并与一个既有 ServiceRevision Draft 原子创建。候选不复制审批或发布状态机：`Planned/PendingApproval/Approved/Activating/Ready/Stale` 由关联 ServiceRevision 投影，提交继续复验 Planner 摘要，审批继续强制不同主体，激活继续走 Kernel Publish，回滚继续创建更高单调 revision。关联修订带安装工作流所有权，通用 Intent 编辑、服务提交、审批和发布入口全部 fail-closed，防止绕过安装专属权限。取消只允许未提交草稿，原子删除服务草稿但保留候选审计；重启会校验候选与修订绑定。候选只保存 Artifact Lock 摘要视图，完整锁复用关联 ServiceRevision，避免在 1 MiB tenant 聚合中重复存储。测试覆盖完整激活/回滚、旧入口旁路拒绝、并发候选拒绝、取消幂等、重启恢复和 Planner 漂移。
- 2026-08-02：P3 完成。Deployment Manager 0.24.0 新增 Workbench 数据驱动跨服务“服务插件”页及 Portal BFF 强类型路由。目标只从当前活动 Application Intent 的应用服务单元派生，批量请求按 Deployment 拆成多个独立候选；同一 Deployment 不并行创建两个候选，避免伪造跨服务原子事务。BFF 从已发布 `ManagementTarget` 固定 logical service、capability 与 controller source，显式拒绝浏览器 `source`、未知字段和物理节点目标；预览、申请、审批、激活/回滚分别要求独立权限。候选详情复用 P2 Preview，列表只在用户刷新时调用 `kernel.deployment.readiness` 投影滚动状态及副本数，不持久化 readiness、不增加常驻轮询。Platform Catalog/Profile、开发身份和授权 Bootstrap 已同步全部 operation 与权限。
- 2026-08-02：P4 完成。新增全栈 Platform 系统插件 `cn.vastplan.platform.artifacts.marketplace`，以一个受治理 Profile 管理最多 32 个按优先级排序的市场 URL；生产远端强制 HTTPS，开发 HTTP 只允许显式 loopback，认证只引用托管凭证并在可信进程中通过 material lease 使用。平台自身 Catalog 使用 `vastplan://platform.artifacts.repository` capability URL，避免 Seed 为内部调用复制 HTTP Token。Marketplace 只负责发现，不成为第二个仓库；外部来源条目先显示为“需导入受信仓库”，完成受治理导入和验签后才开放安装。Portal BFF 新增服务自助路由：deployment/unit 只取自已发布 `ManagementTarget.resource`，浏览器只能提交 change；列表、详情和全部生命周期 operation 再按 `self-service + target` 复核。Deployment Manager 0.25.0 在组合根注入 `approval.policy.v2` Binding，预览冻结精确 Profile Decision；`allowed` 在提交后由策略主体复用既有 Approved 状态，`review-required` 保留 PendingApproval 并由数据驱动表单提交 Provider 要求的证据，`denied` 不创建候选。控制器、自助和开发入口未产生第二套状态机。
- 2026-08-02：P5 完成。Local Plugin Library 源控制器把源码新增、修改、删除分别归一为 `Install/Upgrade/Remove` Development Installation Intent；只有显式启用且匹配插件的 `TestTargetBinding` 会接收意图，新插件还必须由绑定显式设置 `allowInstall`。`platform-dev/installation-watch` 使用独立签名 system caller，经全局能力目录调用 Deployment Manager 的同一候选工作流；能力目录尚未收敛时只对 `capability not found` 做有界等待，不复制另一套开发发布状态机。每个绑定显式携带 `portalTargets`，空列表表示只更新 Backend。
- 2026-08-02：P6 完成。统一安装候选显式携带 `portalTargets[]`：服务自助入口由可信 BFF 固定为当前 Portal，控制器和开发绑定必须明确列出目标，禁止根据服务关联关系向所有 Portal 扩散。Deployment Manager 先让所有目标 Portal Composer 创建隐藏的内部版本并完成 Catalog/模块预热，再发布 Backend，最后逐个提交 Portal Activation；任一准备失败不发布 Backend，提交失败则按逆序回滚已提交 Portal、回滚 Backend 并终止未提交准备。Portal Composer 保留用户 WorkingCopy，不把安装内部版本暴露为普通草稿；调用只允许精确的 Deployment Manager workload 身份。Portal BFF 从已验证的当前 Activation 派生 Generation，并用宿主保留的 `vastplan.portal.activation-id`、`vastplan.portal.generation` CallContext metadata 传给后端；浏览器不能提交或覆盖这两个值，旧页面兼容路由可以据此执行有界排空。单元和进程边界测试覆盖成功顺序、Portal 提交失败补偿、旧 Activation 保留、WorkingCopy 不被覆盖及幂等重试。
- 2026-08-05：P7 完成。Kernel Preview 从精确候选制品生成 DataModel Catalog，Installation Preview 统一展示安全增量、签名迁移、备份要求与回滚模式，并把 Schema Impact digest 纳入审批。Deployment Manager 0.28.0 在发布时生成宿主专属 Schema Activation；Node Agent 在候选路由注册前使用 Record Store 1.2.0 再规划、执行并复核迁移账本，运行时计划漂移或证据缺失都会保留旧实例。安装激活开始等待精确 Backend readiness，失败先回滚 Backend 再终止 Portal 准备，避免把“期望态已写入”误报成全栈激活完成。
