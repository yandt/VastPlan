# ADR-0204：ActualState 生产兼容基线与连续迁移

- 状态：已采纳
- 日期：2026-08-08
- 关联：[ADR-0032](ADR-0032-Backend插件生命周期实际态v2.md)、[ADR-0038](ADR-0038-Backend可复现发布与运维交付.md)、[ADR-0100](ADR-0100-制品生命周期引用保护与垃圾回收.md)、[ADR-0101](ADR-0101-离线Bootstrap-Inventory与LKG推进.md)

## 背景

Node Agent `ActualState` 是每个节点的本地恢复真源，并复制到 NATS KV 供控制面观察。开发期间格式从 v1 演进到 v4：v2 引入封闭生命周期与候选状态，v3 引入 Assignment 制品引用 outbox，v4 引入 Bootstrap Inventory 发布进度。v1-v3 均产生于系统首次生产上线之前，仓库只保留若干不再活动的开发 smoke 快照，没有外部兼容责任。

旧实现仍可读取 v1-v3，并把 v2/v3 直接反序列化到当前结构。该路径没有生产收益，还会让开发期偶然格式变成永久承诺；同时，现有文档没有统一规定产品版本与状态格式版本的关系、跨版本升级、滚动发布和旧迁移退出条件。

## 决策

### 1. v4 是首个生产兼容基线

首次生产发布前只支持读取和写入 `ActualState.version = 4`。开发期 v1-v3 不构成升级承诺，当前 Backend 对其 fail-closed；历史 smoke 文件可以保留用于取证，但不能作为启动、预检或回滚输入。

ADR-0032 第 4 节和 ADR-0038 中关于 v1 读取并写回 v2 的决定至此被取代。两篇 ADR 对生命周期状态机、发布预检、备份和回滚的其他决定继续有效。

### 2. 三类版本不得混用

- **产品版本**：Backend 发布 SemVer，用于发布支持范围和升级路径，例如 `1.3.0`；
- **状态格式版本**：`ActualState.version`，只用于选择本地状态解码与迁移链；
- **最后成功发布版本**：由 Deployment/Release Ledger 持有，用于发布、回滚和支持诊断，不作为状态迁移起点。

首次安装时不存在旧 ActualState，必须直接创建该产品版本的当前格式。不同客户可以从不同产品版本首次上线，不需要先伪造 v4 再逐级迁移。已有节点升级时以文件中的状态格式版本为唯一迁移起点，不能根据产品版本猜测。

当首次引入 v5 时，状态应增加可诊断的精确写入者产品版本或构建身份；该字段只解释来源，不改变迁移选择仍由格式版本决定的规则。

### 3. 每次格式升级提供连续迁移边

产生 v5 及后续格式的同一次改动必须声明：

- `currentWritableVersion`：目标二进制唯一写入的格式；
- `minimumReadableVersion`：目标二进制承诺直接升级的最老生产格式；
- 每条连续、显式的 `vN -> vN+1` 迁移函数；
- 每条迁移边的真实旧格式夹具、字段保留测试和非法输入测试；
- 产品发布版本到可接受源格式范围的发布矩阵。

跨版本升级按连续边组合，例如 v4 直接升级到 v7 时执行 `v4 -> v5 -> v6 -> v7`。迁移函数必须确定、无外部副作用、输入输出版本固定，并在每一步后验证目标格式。不得用 `case 4, 5, 6` 直接反序列化到当前结构来冒充迁移。超出 `minimumReadableVersion` 时必须要求桥接发布，不猜测或静默丢字段。

当前只有 v4 一个生产格式，不提前保留空迁移注册表；第一次格式升级必须在同次改动中建立上述协议。

### 4. 预检与执行分成两个阶段

发布前 `validate -kind actual-state` 使用目标二进制读取真实状态、解析完整迁移链并演练最终校验，但不得修改源文件或产生运行副作用。

目标二进制首次启动时，必须在 reconcile、插件启动、路由切换、引用发布和 NATS ActualState 写入之前：

1. 获取 Node Agent 单实例锁；
2. 读取并核对源格式；
3. 创建 owner-only 的原子回滚备份；
4. 在内存中执行完整迁移链并验证当前格式；
5. 原子写回本地 Primary；
6. 才允许正常运行和复制到 NATS。

ActualState 格式迁移只处理节点恢复状态。插件私有业务状态、Shared State、Record Store 或数据库 Schema 继续使用各自的受治理迁移事务，不得塞入本地格式迁移函数。

### 5. 滚动升级先部署 Reader

ActualState 会复制到 NATS，滚动升级期间可能同时存在多个格式。格式升级必须先让 Controller、支持工具和其他观察方具备新旧格式读取能力，再通过发布门禁允许 Node Agent 写入新格式。破坏性变化需要显式 feature gate；首个新节点不得立即发布旧控制面无法读取的状态。

本地迁移是单向的。二进制回滚必须同时恢复迁移前备份，旧二进制不得读取未知新格式，也不提供反向迁移伪装安全回滚。

### 6. 旧迁移按证据退出

生产迁移边只有同时满足以下条件才能删除：

- 受支持产品版本的最低源格式已高于该边；
- 生产节点本地文件与 NATS Actual KV 盘点中该源格式为零；
- 升级备份和回滚观察窗已经结束；
- 支持矩阵已明确要求更老安装先经过桥接发布；
- 删除代码、夹具、运维说明和支持声明在同一次改动完成。

不能仅凭仓库当前没有旧夹具，或某个开发环境已经升级，就推断生产状态可以退役。

## 结果

- 开发期偶然格式不会成为永久生产负担，v4 形成清晰的首次上线基线；
- 不同客户可从任意受支持产品版本首次安装，已有安装按自身状态格式升级；
- 跳过产品版本仍可通过目标二进制携带的连续迁移链安全升级；
- 发布预检、启动期原子迁移、滚动升级和回滚拥有明确顺序；
- 未来兼容代码只能基于正式支持矩阵和生产证据增加或退出。
