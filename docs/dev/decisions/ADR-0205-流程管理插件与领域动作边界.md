# ADR-0205：流程管理插件与领域动作边界

- 状态：已采纳
- 日期：2026-08-08
- 关联：[ADR-0189](ADR-0189-审批策略Provider与声明式规则.md)、[ADR-0193](ADR-0193-第一方插件边界与Capability契约版本.md)、[ADR-0203](ADR-0203-受治理默认UI-Provider替换.md)

## 背景

Portal Composer 目前把 `Draft -> PendingApproval -> Approved -> Published -> Release` 固定在领域状态机中。其他需要审批、复核、等待、通知或定时处理的功能若复制这套代码，会形成多套流程定义、任务箱、审计和恢复语义；若把现有 fail-open Hook 当作流程步骤，又会让配置者绕过权限、CAS 和签名边界。

流程的中间态应可按服务在线配置。业务插件应能只声明资源契约、校验规则和最终动作，不必调用流程启动 API，也不必重复实现候选、修订与流程状态 Repository。状态不会消失，而是由通用资源服务、流程插件和最终领域系统分别持有。

## 决策

### 1. 独立全栈流程插件与中立治理入口

新增 `cn.vastplan.platform.workflow.orchestrator`。插件独立拥有流程定义修订、服务绑定、运行实例、人工任务和审计记录，使用外部共享 Record Store 持久化，并以可信独立进程运行。服务未选择该插件时，不获得流程设计、任务箱或受管流程能力。

受治理操作通过中立的 Governed Operation Gateway 进入。业务插件的准备操作只返回标准 `GovernedResource`，由 Gateway 在准备成功后调用已选择的编排 Provider。现有 `hook` 仅支持 fail-open 的调用前否决和调用后摘要观察，不能查看完整结果、替换响应或承担失败关闭的耐久流程，因此不得复用为该 Gateway。

### 2. 声明与执行分离

功能插件通过签名 Manifest 的 `contributes.backend.workflowFeatures` 注册可纳管功能点和封闭的领域动作目录。该贡献只进入可信 Inventory，不执行代码。

每个功能点还可声明未绑定策略。默认 `deny`；显式选择 `direct` 时必须指定目录内的终态动作。直通仍由流程插件创建耐久实例并记录审计后调用领域动作，Gateway 和领域插件都不得把“未找到绑定”解释成自行放行。

流程实例只可引用目录中的动作 ID。编排器通过 `workflow.action.v1` 调用动作所有者；不得保存 URL、脚本、插件 ID 覆盖值或任意 hook payload。hook 只能用于通知已有事实，不能决定流程流转或直接发布领域对象。

### 3. 资源、流程与最终领域真相分别持有

- Governed Resource Store 拥有通用 WorkingCopy、冻结 Candidate、不可变修订、摘要、生命周期 CAS 与资源审计；业务插件仍在语义上拥有资源 Schema 和领域校验规则。
- 流程插件拥有 Definition Revision、Binding、Instance、Task、Token 与流程审计。
- 最终领域系统拥有用户账户、Portal Activation、部署结果等真正生效的业务事实。
- 启动流程时必须携带冻结资源引用和摘要；实例固定绑定精确 Definition Revision。
- 终态领域动作执行时，Gateway 重新读取候选并验证摘要和 CAS，动作实现重新验证领域前置条件。流程完成不能代替最终领域动作成功。

业务插件可以不包含持久化代码，但不能把领域真相转移给流程实例。通用资源存储只保存受治理资源与修订，不成为任意业务数据库。

### 4. 定义修订不可变

已发布的流程定义不可原地修改。在线编辑产生新的连续修订；服务与功能点绑定精确修订，新实例使用新绑定，运行中实例保持原修订。跨版本升级由流程插件的数据模型迁移负责，不在读取时猜测旧结构。

### 5. 三层节点模型

节点分为三层：

1. Workflow Core 内置节点拥有不可替换的控制与耐久语义，包括开始/结束、人工任务、签名动作、决策、定时器、事件等待、分叉/汇合和子流程。
2. 外部插件优先贡献声明式 Node Template。模板在定义发布时编译为内核节点，运行实例不依赖模板插件在线。
3. 无法由内核节点组合表达的能力才贡献受限 Node Provider。Provider 不保存流程游标，只能返回 `Complete`、`Wait`、`RetryAfter`、`Fail` 等由编排器解释的耐久效果。

外部贡献不能增加新的持久化语义、任意调用目标或自定义恢复协议。一个物理插件可以贡献多个同边界节点；禁止为每个纯逻辑节点创建独立进程。

### 6. 语言与运行形态

- **Go（编排器与通用资源服务采用）**：与 Plugin Host、Record Store SDK、CallContext 和现有领域插件同进程模型，适合 CAS 状态机与高并发任务处理，资源开销最低。
- **Node.js**：适合流程设计 UI，但作为耐久调度核心会引入额外 Runtime、事件循环阻塞与双语言运维面。
- **Python**：适合数据/AI 节点生态，但本能力的核心是确定性事务和协议编排，启动与资源成本不占优。

后端采用 Go 可信独立进程；默认管理 UI 使用 TypeScript Workbench。外部 Node Provider 可按场景选择 Go、Python、Node.js 或其他已支持 Runtime，并通过稳定 RPC 契约返回受限效果；不得把语言或 Provider 模式开关传入领域层。

## 结果

- 审批等中间流程可按服务在线管理，具体功能只注册资源、准备入口和允许动作。
- 业务插件不再显式调用 `start`，是否绑定流程对其透明。
- 领域发布不被编排器越权，摘要、权限和 CAS 仍由对象所有者强制。
- 流程实例可审计、恢复和升级，不依赖内存 hook 链。
- 常见扩展通过模板编译获得插件生态能力，同时保持运行时可恢复；Provider 只承担不可组合的外部行为。
- Portal 的旧固定审批状态将在迁移完成后退化为兼容读模型，不再是流程真相源。

## 交付说明

ADR 首次落地采用兼容迁移：Portal 的准备适配器暂时继续在原 Repository 冻结 Publication，组合入口在选择工作流服务时将提交端口绑定到 Governed Operation Gateway，未选择时保留原直通接口。通用 Governed Resource Store 和旧状态迁移是后续独立阶段；在该阶段完成前，不把 Portal 的兼容候选存储描述为已经移出业务插件。
