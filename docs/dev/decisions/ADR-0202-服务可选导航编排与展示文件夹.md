# ADR-0202：服务可选导航编排与展示文件夹

- 状态：已采纳
- 日期：2026-08-08
- 关联：[ADR-0190](ADR-0190-Portal语义导航策略与服务复用.md)、[ADR-0191](ADR-0191-统一插件安装意图与多入口生命周期控制.md)、[ADR-0203](ADR-0203-受治理默认UI-Provider替换.md)

## 背景

ADR-0190 让插件通过签名 Manifest 自治声明 `root → child? → page` 导航树，Portal 只保存对已安装节点的有界覆盖。这消除了中央菜单树随插件增删同步的问题，但把低层 `navigationOverrides` 放进 Portal 综合编辑表单，不适合频繁的信息架构编排，也不能由服务自身的获授权管理员独立使用。

服务还需要把来自不同插件的根菜单收缩为一个可命名、可选图标的文件夹。直接把文件夹变成新的父节点会形成 `folder → root → child → page`，破坏现有最大深度；把多个 root 交给普通树形菜单又会给原本的 `root → page` 视觉上补出一个可展开层。

## 决策

### 1. 文件夹属于展示投影，不属于导航语义树

签名插件目录、页面 `parentMenuRef`、`activeNavigationPath`、路由和权限裁剪继续只认识 `root → child? → page`。Shell Composition 在规范导航树之后再生成 `NavigationCollection` 展示模型：

- 普通入口是只包含一个 root 的 collection；
- 文件夹是包含两个或更多 root 的 collection；
- 文件夹不能成为页面或菜单的 `parentMenuRef`，也不进入深链路；
- 账户锚点、child 节点和跨 zone 节点不能成为文件夹成员；
- 同一个 root 在一个作用域内最多属于一个文件夹。

活动页面仍解析到原始 root。布局只根据该 root 找到对应 collection 并选中展示入口，不能重写活动路径。

### 2. 右侧菜单使用分区，不增加可展开层

标准侧栏点击文件夹后，右侧面板一次展示文件夹中的全部 root。每个 root 是不可交互的语义分区标题：

- `root → page` 在分区下直接显示 page，不生成 root submenu；
- `root → child → page` 在分区下只保留原 child submenu；
- root 同时拥有直挂 page 与 child 时，直挂 page 与 child 并列；
- 顶部导航和移动端使用同一分区数据，只改变承载位置。

因此文件夹不会把三层导航扩成四层，也不会把两层导航伪装成三层。

### 3. 文件夹名称和图标

文件夹具有稳定 ID、默认名称、受支持 locale 的名称覆盖、可选语义图标和顺序。未指定图标时，Shell 按成员 root 的最终有效顺序取前四个可见图标，生成固定的 `2×2` 组合图标；不足四个时只绘制已有图标。组合图标只复用已验证的语义图标或安全 AST，不接受原始 SVG、URL 或 React 组件。

### 4. 可选全栈插件和作用域

导航编排由独立可选全栈应用插件提供。服务未选择该插件时，不注册管理页面、不暴露管理 API，也不产生文件夹投影，Portal 使用插件默认导航。

配置按 `tenant + portalId + managedServiceId` 隔离。Portal 管理员可以管理 Portal 已绑定且授权的服务；服务管理员只能通过当前可信 Portal 的 Management Binding 管理自身服务。读、编辑和发布使用独立权限。浏览器不能提交逻辑服务、路由域、部署或单元目标。

同一个 Portal 绑定多个服务时，各服务只能编排归属于自身页面实例的菜单。运行时以 `managedServiceId + pluginId/nodeId` 识别可编排实例，避免一个服务修改另一个服务复用的同名插件菜单。

### 5. 发布与兼容

导航编排直接从当前 Activation 克隆一个 Composer 内部候选，并以当前 Activation ID 做 CAS 后进入 Portal 发布；它不创建、保存或覆盖用户 Portal WorkingCopy。文件夹投影、插件目录、页面和 UI Contract 随同一 Portal Generation 原子切换，不允许运行时另取一份可变配置。

内部候选采用 `prepare → materialize → commit`，并保留 `abort/rollback` 状态。并发 Portal 发布会让 commit 失败关闭，管理员必须基于新的 Activation 重新读取和提交。

Portal 综合编辑表单不再显示 `navigationOverrides`。历史 Activation 继续按原字段读取；安装导航编排插件后，可在后续兼容迁移中把既有覆盖导入独立编排页面。导入和清除旧字段必须属于同一个内部候选，失败时保留旧 Activation。

卸载被引用插件或导航编排插件时，ADR-0191 的 Portal 准备阶段必须先验证候选投影。未知成员、重复成员、跨 zone、账户锚点、child 成员和空文件夹均使候选失败，不在浏览器静默猜测。

### 6. 默认 UI 可由插件替换

导航编排插件内置一个数据驱动 Workbench 管理页，同时按 ADR-0203 声明 `frontend.page + single` 的 UI Provider 扩展点。没有替换贡献时注册默认页；存在一个兼容贡献时只注册贡献者页面。替换 UI 仍调用同一管理 API、使用同一权限和发布状态机，不能替换 Shell 或注入任意 React 内容。

## 语言与运行方式

- Go 后端：原生 SDK、静态类型契约、低常驻资源和现有 Portal Composer 调用链最匹配，适合短事务、强校验的服务适配器；选用。
- Node.js 后端：可与前端共享 TypeScript 类型、迭代快，但会为很薄的适配器增加独立 Worker Runtime 与序列化边界，本功能没有 Node 生态依赖；不选。
- Python 后端：适合算法、数据和 AI 生态，但本功能没有对应依赖，启动与资源成本也高于原生适配器；不选。
- 前端使用 TypeScript 和 Workbench 数据驱动页面；浏览器 UI 不引入第二种框架。
- Go 后端复用 Portal Composer 的 CAS、候选、发布和回滚能力；插件只拥有服务范围授权与导航编排工作流，不复制 Portal 状态机，也不自持可变导航状态。
- Shell、标准侧栏和顶部导航继续使用 TypeScript/React；Renderer 只增加受治理的菜单分区和组合图标呈现。
- 后端以服务范围 active-active 原生实例运行，状态写入只通过远端 Portal Composer；前端贡献随 ADR-0191 的同一全栈候选进入明确的 Portal target。

## 备选方案

### 把文件夹加入真实导航树

需要升级全部导航深度、路径和布局协议，并使插件目录依赖一个外部可变父节点；拒绝。

### 仍由 Portal Composer 综合表单管理

实现较少，但服务选择插件与能力是否存在不一致，服务管理员还会获得过宽的 Portal 组合权限；拒绝。

### 浏览器运行时读取可变文件夹状态

更新快，但会产生新页面与旧目录、不同副本与不同用户看到不同导航的混代；拒绝。

## 结果

- 文件夹可收纳不同插件的菜单，但不改变插件自治目录和页面路由。
- `root → page`、`root → child → page` 和混合 root 都不会因为收纳而增加导航层级。
- 服务未安装插件时完全没有该能力；安装后，平台管理员与服务管理员走同一受限服务工作流。
- 文件夹配置作为 Portal Generation 输入接受发布、审计、回滚和热换代校验。
