# ADR-0194 平台控制数据库与声明式数据分层

- 状态：已采纳
- 日期：2026-08-05
- 关联：[ADR-0095](ADR-0095-Database-Runtime多Provider连接池与集群事务.md)、[ADR-0109](ADR-0109-种子访问与企业身份Provider分离.md)、[ADR-0133](ADR-0133-Credentials保持Leader与Active-Active前置条件.md)、[ADR-0193](ADR-0193-第一方插件边界与Capability契约版本.md)

## 背景

开发态仍有插件把运行状态直接写入本机 JSON 文件。现有 `state.shared.v1` 已统一身份派生、CAS 和错误语义，但生产默认 Provider 是 NATS KV，SQL Provider 尚未实现。与此同时，Database Runtime 只有参数化 SQL 和事务契约，插件仍需重复编写数据类型、Repository 和迁移代码。

## 决策

1. 种子服务采用两阶段启动。Bootstrap 阶段只启动 Seed Access、最小认证授权链、静态 Portal 必需模块和 Database Runtime；SQL Shared State 就绪后才启动依赖平台状态的完整组合。
2. Database Runtime 内部增加 SQL Shared State、Record Store 和 Schema Controller 模块，不建立新的运行插件。Backend Kernel 只保留可绑定的 Shared State Store SPI 和分阶段启动机制。
3. 平台控制数据库使用保留的 `PlatformControlStoreProfile`。非敏感配置保存在受保护的本机 Bootstrap Profile；Linux 生产秘密使用 systemd credential，开发允许 0600 文件。Seed verifier、恢复根和控制库自身解密根不得写入控制数据库。
4. SQL 是种子生产默认 Shared State Provider；NATS KV 保持可选协议；File 仅用于单测、未初始化开发环境和明确的 Seed/Recovery 根状态。Provider 不可用时 fail-closed，禁止回退文件形成双真相源。
5. PostgreSQL 和 MySQL 同批支持。平台控制数据使用独立逻辑数据库或独立 schema；普通插件必须通过 Connection Manager 获得业务 `connectionRef`，不能选择保留控制库连接。
6. 数据能力严格分为 `DataModel -> Repository -> Application Workflow`。DataModel 不声明页面、权限和业务动作；Repository 不含业务规则；所有对外操作即使只有简单 CRUD 也必须经过显式 Workflow。
7. `data.model.v1` 是语言中立签名契约。Go 工具在构建期验证模型并为插件实际语言生成 Go、TypeScript 或 Python 强类型 Repository 源码；生成物按模型分文件提交，CI 复生成检查漂移。
8. 安全增量 Schema 变化可自动执行；删除、改类型、收窄约束和数据重写必须使用签名迁移、备份前置检查、单一 Schema Controller 和持久迁移账本。
9. 数据库访问逻辑集中于统一 Database Runtime 契约，物理上 active-active 多副本运行。各实例维护本地池，普通调用本地优先并允许远端故障转移；事务保持实例亲和；Schema 迁移单写。
10. 首次 Platform Control 配置可以显式选择“数据库不存在时创建”。连接测试始终只读；`Configure` 仅在 generation 0 且测试返回稳定 `database_not_found` 时执行 `Provision -> Test -> Initialize -> Commit`。PostgreSQL 通过 `postgres` 维护库建库，MySQL 通过无默认 database 的连接建库；建库幂等但绝不隐式删除数据库。启动、恢复、普通连接和既有 Profile 更新均不得触发 Provision。
11. `engineering/governance/first-party-plugin-boundaries.json` 中的 `stateOwnership` 是第一方生产插件状态归属的机器可验证清单。每个插件必须声明 Manifest `stateModel` 镜像、自己拥有的耐久真相源、短时状态和本地文件边界；`stateModel` 只描述运行拓扑，不能被当作“数据一定在数据库”的替代证据。新增或删除插件、改变真相源或新增本地文件时必须同步该清单和架构门禁。
12. 从文件迁移到 Shared State/Record Store 时，旧开发状态文件必须进入显式退役清单。开发编排器只对清单中的普通文件执行可回滚隔离，不读取、不导入、不静默覆盖；符号链接和其他特殊文件一律拒绝。生产路径重新出现退役文件名由架构门禁阻断。

## 影响

- 种子运行状态可以由企业数据库备份、复制和恢复；
- 普通服务不持有数据库驱动、密码或独立连接池；
- 插件只需声明数据模型即可获得类型安全的数据读写层，但不能绕过业务流程；
- 当前开发状态不迁移，允许清理后重新初始化；未来生产迁移必须另走签名迁移和恢复流程。

## 实施记录

- 2026-08-05：P2 建立 `data.model.v1` 严格 Schema、Go 校验器和 Go/TypeScript/Python 确定性生成器；Manifest 使用外部路径与 SHA-256 绑定模型，架构门禁复生成已提交 Repository 并检查零漂移。首个真实模型由 Database Connection Manager 提供。Record Store、Schema Controller 和 SQL Shared State 尚属于后续 P3，不能把类型生成误记为持久化迁移完成。
- 2026-08-05：P3a 冻结 `record.store.v1` 请求边界和 Database Runtime 内部 Record Store 模块。模型目录按 generation 原子替换并复核 owner、模型身份和 SHA-256；SQL 只由 PostgreSQL/MySQL 方言编译器从白名单字段生成，tenant/service scope 由可信调用上下文注入。Schema 分类器仅自动接受建表、可空字段和非唯一索引，其他变化返回 manual。执行 capability、幂等账本、迁移单写和 SQL Shared State 未完成前不对外宣称 Record Store Ready。
- 2026-08-05：P3b 已实现 Database Runtime 内部 Record Store 执行面，包括 CRUD、受限 List、Batch、实例亲和 UnitOfWork、幂等账本和事务内 Outbox；Schema Controller 使用数据库 advisory lock、持久 migration ledger 和 SYSTEM/credential evidence 约束自动安全迁移；SQL Shared State 已按现有 `sharedstate.Store` 的 1 MiB、CAS、分页、作用域隔离和 fail-closed 语义实现 PostgreSQL/MySQL 模块。`data.model.v1` 提升到 `1.1.0`，索引字符串必须声明 `maxLength`，TypeScript `int64` 固定生成为 `string`，避免 MySQL 索引越界与 JavaScript 精度漂移。Record Store 和 SQL Shared State 仍未写入公开 Manifest 或主入口：P4 注入保留控制库会话、P6 完成多副本目录同步后才能宣称 capability Ready。破坏性签名迁移包仍属于 P3 后续检查点。
- 2026-08-05：P3c 增加 `data.migration.v1` 和 Manifest `backend.dataMigrations[]`。迁移文件的 SHA-256 由已签名插件 Manifest 固定，可信宿主同步时还必须投影已验证 Plugin Inventory digest 与 Artifact SHA；Runtime 原子校验模型和迁移来自同一制品。破坏性迁移显式声明备份、审批和可安全重试，SQL 限定为无注释、无分号的单条受限语句且不能修改 Runtime 内部表；执行时还必须同时持有连接 leader、备份完成和审批完成三类 service evidence。迁移账本记录成功迁移 ID，同一目标模型重放直接返回 Ready。P3 实现面已闭合；本机 Docker daemon 在真实 PostgreSQL/MySQL 矩阵准备阶段无响应，因此该矩阵仍列为环境阻塞，不能记为已通过。
- 2026-08-05：P4a 建立 `PlatformControlStoreProfile` 严格契约、owner-only generation CAS 文件 Store、systemd credential 与开发 owner-file 两种 `SecretSource`、`Test -> Initialize -> Commit -> Bind` Controller，以及只能向前切换、未绑定即 fail-closed 的 `sharedstate.BindingStore`。首次失败不提交 Profile、不绑定本地 JSON；替换候选失败保留旧 Ready generation；已绑定外部 Provider 故障时禁止回退文件。Database Runtime 远端适配、Bootstrap Tier 和配置 UI 仍属于 P4 后续。
- 2026-08-05：P4b 在 Database Runtime 内部增加 `platformcontrolbootstrap` 适配器，复用 PostgreSQL/MySQL Provider Registry、本地池和 pinned session 完成 Test、迁移锁、限定 schema 建表、Open/Probe 与 SQL Shared State 装配。适配器只返回可关闭的 `ManagedStore`，Profile 提交或绑定失败会立即释放候选池；TLS 增加校验证书链但不校验主机名的 `verify-ca`。`Bootstrapper/ManagedStore/SecretSource` 位于中立 Library，插件与 Kernel 都不反向依赖对方实现。该能力仍是 Database Runtime 内部模块，不新增插件，也不允许 Kernel 引入数据库驱动。公开 Database Runtime Capability 提升至 `1.2.0`，插件提升至 `0.9.0`。
- 2026-08-05：P4c 完成独立进程边界：Database Runtime 贡献仅固定 SYSTEM caller 可用的 SQL Bootstrap 与 Shared State Capability，宿主以 `RemoteBootstrapper/RemoteStore` 重新适配稳定 Store SPI。Deployment/Assignment 新增默认 `full` 的 `startup_tier`，Node Agent 在 Store Ready 前只激活显式 Bootstrap 单元；Controller 订阅可信能力目录 topology change 幂等恢复，不增加轮询。该检查点先固定单副本，后续 P6 已解除此临时限制。
- 2026-08-05：P4d 把配置面接入同一两阶段协议。Controller 的 `Status / TestCandidate / Configure` 通过受限 Kernel Service 只开放给 Connection Manager；Portal 只能经 Management Binding、角色权限和 CSRF 保护的固定 BFF 路由调用。测试候选不执行初始化或提交，配置候选继续遵守 Test、Initialize、Profile CAS 和 Bind 顺序。平台控制数据库页面属于现有数据库全栈插件，使用 Workbench Form Page 且只提交 systemd credential name 或 owner-only 文件引用，不引入密码明文或新的普通应用插件。
- 2026-08-05：P5 第一批把 Connection Manager 的本机 JSON 真相源迁移为按租户 Shared State CAS。持久化协议在插件组合入口固定，所有正常管理 Workflow 先加载当前 Store revision，再以 leader-fenced create/update 推进连接定义、凭证候选、Runtime publication outbox 与回收队列；不可用或冲突均 fail-closed。Platform Control 的状态、测试和配置操作继续绕过该业务状态协议，只进入受限内核端口，避免 Bootstrap 循环依赖。当前聚合保留 Saga 原子边界；DataModel 生成的独立 Repository 将用于后续拆出的记录数据，不能机械拆散凭证与发布事务。
- 2026-08-05：P6 连接预算不再使用每实例固定上限。Database Runtime 启动组合根从用户配置的 `clusterMaxOpen` 与 Scheduler 根据 Deployment/Autoscaling 派生的可信 `clusterMaxReplicas` 一次生成每实例 ManagerPolicy，避免用户重复填写副本数导致预算漂移；Pool Manager 原有的 generation 预算同时统计活动代、排空代和关闭失败保守占额，因此 active-active 扩容与双代滚动升级的最坏物理连接总量不超过集群硬上限。预算不足以为每个副本保留两个 generation 时拒绝启动，副本之间不共享 socket，也不在运行中借用连接额度。
- 2026-08-05：P6 完成 Platform Control Store 多副本装配。可信宿主从强身份能力目录取得精确实例并按同节点优先排序；初始化只在首实例执行一次 Schema 准备，其余实例幂等 Open。全部成功后才原子替换共享的已打开副本集合，既有 Store 随 topology change 更新而无需重新绑定 Kernel SPI。每次 SQL Shared State 调用固定目标实例，仅传输错误允许顺序故障转移；CAS 和其他应用错误不重放。Record Store 的普通调用继续本地优先，UnitOfWork/事务句柄保持 owner 实例亲和，owner 丢失返回 `transaction_lost`。
- 2026-08-05：P5a 将 OTP `configuration.v1` Active/Candidate 与 Webhook Delivery `configuration.resource.v1` Profile Saga 从直接文件迁移到 fenced Shared State。OTP 使用 service scope 保存非敏感配置控制状态，验证码 Challenge 继续只在有界内存中；Webhook 按 tenant scope 分值，避免跨租户聚合突破 1 MiB 上限。两者均删除生产 `stateFile`，首次业务调用先恢复耐久状态，Store 不可用或 CAS 冲突时 fail-closed。
- 2026-08-05：P7 复核发现 Record Store 虽已有实现与单测，但未进入 Database Runtime 生产组合。0.12.0 在同一签名制品内正式注册 `foundation.data.record-store@1.0.0`，并同步 Manifest 强类型工具目录；增长型插件数据只有在可信 Inventory 同步模型后才能调用，未同步模型继续 fail-closed。
- 2026-08-05：补正并完成上述生产链：Record Store 线协议已有增量能力，故正式契约版本固定为 `1.1.0`，Database Runtime 提升到 0.13.0，避免覆盖已发布的 0.12.0 稳定制品。Controller 从 Deployment 锁定的精确制品读取并校验 DataModel/签名迁移文件，生成有界同代 Inventory，只向声明 `foundation.data.record-store@1.1.0` 的 Runtime 注入宿主保留配置；Node Agent 在候选路由发布前以 Host 创建的 SYSTEM 身份和 Inventory 摘要证据同步目录，并先从插件配置投影中摘除保留字段，配置方与插件进程均不能伪造目录。
- 2026-08-05：P5b 将 Authentication Broker 的 Provider Profile、Lifecycle、测试/审批证据和已发布 Catalog 从可写本机文件迁移到 service-scope fenced Shared State，领域 generation 与 Store revision 一致，数据库不可用和 CAS 冲突均 fail-closed。Seed Catalog 文件缩减为只读 Bootstrap/Recovery 根，只在 SQL Shared State 明确从未发布 Catalog 时回退；超时、损坏或数据库故障不得触发 JSON 回退。短时认证 transaction 与一次性 Assertion 继续留在 Leader 有界内存。
- 2026-08-05：P4e 完成开发编排器的真实两阶段启动：Recovery Tier 精确包含认证 Broker、授权 Session、Connection Manager 与 Database Runtime 四个单元；Recovery Capsule 以单元 applied revision 评估低层就绪；Portal Host 在恢复层就绪后立即提供已认证、CSRF 保护且目标能力由宿主固定的平台控制数据库页面/API；首次人工配置等待只受进程 context 控制。SQL Store 绑定通过有界事件触发既有 Node Agent 组合链继续收敛，不复制启动流程。实机验收同时发现并修复 Go `schema_version=2` 能力目录与 Node SDK 只接受 v1 的跨语言契约漂移，Node 现强校验 ArtifactIdentity、ContractIdentity 和 fingerprint。PostgreSQL/MySQL 真实初始化与多节点竞争仍需后续矩阵验收。
- 2026-08-05：P5c 将 API Exposure 的 revision、Route Key tombstone 与审批审计从 64 MiB 本机 `stateFile` 迁移到 leader-fenced、service-scope Shared State CAS，并将聚合上限收紧到统一的 1 MiB。`gatewayCatalogFile` 仅保留为由当前可信 Contract Catalog 重建的本机派生投影；新 Leader 首次调用及 dirty journal 恢复会重建，不再把该文件或旧 JSON 当成治理真相。Endpoint Lease 与一次性 Ticket 继续按设计留在有界内存。插件提升至 `0.8.0`，服务状态模型同步为 `external-shared`。
- 2026-08-05：P3d 修正 `platform-control` DataModel 仅声明但运行期拒绝的缺口。Database Runtime 0.14.0 让 Bootstrap 候选池同时实现 Shared State 与受信 Platform Record Store 会话端口，后者不暴露 pool、driver、DSN、CredentialRef 或秘密；模型必须来自同代已验证 Inventory 且调用插件必须匹配 owner。Record CRUD、Batch、UnitOfWork、Outbox 与 Schema Controller 复用同一池和 generation，旧 generation 关闭后事务稳定返回 `transaction_lost`。PostgreSQL 仅由可信 Bootstrap Profile 注入受限 `search_path`，MySQL 继续要求 schema 等于 database，确保业务 DataModel 与 Runtime 内部账本落入平台保留命名空间。
- 2026-08-05：P3e 将安全 Schema 准备纳入 Platform Control 候选提交前流程。Runtime 0.14.1 在候选池完成 Shared State 基础表初始化后，按稳定模型 ID 顺序为同代 `platform-control` DataModel 执行 Schema Controller 已分类为安全的建表/增量计划；任一模型需要人工迁移或执行失败时，候选池立即关闭，Shared State 与 Record Store 两个 binding 均不切换。破坏性迁移继续必须携带签名迁移、备份和审批 evidence，不能借 Bootstrap 自动执行。
- 2026-08-05：P5c 将 Interaction Broker 从单个可写 JSON 聚合迁移为 `platform.interaction.record` DataModel。每项交互独立持久化，Repository 只执行 owner/tenant 约束下的 Create/Get/List/Update CAS；Workflow 保留来源授权、呈现资格、过期、响应校验和唯一终态规则。并发响应由数据库 revision 决出唯一成功者，重启复用数据库状态，内存 watcher 只作 leader 内延迟优化而不再是真相源。
- 2026-08-05：P7 状态边界门禁开始收口。Connection Manager 删除生产源码中仅供旧测试使用的 JSON Store，生产组合只注入 fenced Shared State 协议；File Provider 移入 `_test.go`。架构测试扫描所有 `stateModel=external-shared` 第一方插件，任何本机持久写入都必须显式归类为 Bootstrap/Recovery 根、Provider 私有文件或可重建投影，未分类写入直接阻断构建。Authorization Policy 首次导入文件、签名快照和 API Exposure 派生目录均已标注真实边界。
- 2026-08-05：P7 产品投影进入运行 Catalog。Backend Platform Profile 以强类型 `productCapabilities` 声明一个 `platform.database` 产品入口，入口固定为 Connection Manager，支撑制品包含 Connection Manager 与 Database Runtime；内部 Provider/Record Store/SQL Shared State 不成为用户可选插件。校验和架构门禁确保产品投影只能引用 Profile 已装配制品且一个制品不能重复归属多个产品能力包。
- 2026-08-05：P7 真实数据库门禁扩展为四阶段矩阵：Provider/Record Store/连接池故障、Platform Control 多副本并发初始化、关闭所有池后的完整 Runtime 重开，以及 PostgreSQL/MySQL 原生事务一致备份、删除原命名空间、隔离恢复和 CAS 数据复核。集成测试默认跳过，唯一脚本在 Docker daemon 五秒内无响应时立即失败；因此测试基础设施完成不等于真实验收已通过，发布证据必须来自该脚本的一次完整成功执行。
- 2026-08-05：首次真实运行发现 MySQL 停机可稳定返回 `connection_refused`，且旧池 Probe 不能作为容器重启后新调用的唯一就绪证据。故障契约现在接受 `connection_refused / connection_unavailable / deadline_exceeded` 三种可重试停机结果；恢复门禁必须重新创建连接池并 Probe 成功，Provider 基础集成也固定在故障注入前运行。
