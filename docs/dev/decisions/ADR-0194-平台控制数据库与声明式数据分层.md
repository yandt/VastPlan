# ADR-0194 平台控制数据库与声明式数据分层

- 状态：已采纳
- 日期：2026-08-05
- 关联：[ADR-0095](ADR-0095-Database-Runtime多Provider连接池与集群事务.md)、[ADR-0109](ADR-0109-种子访问与企业身份Provider分离.md)、[ADR-0133](ADR-0133-Credentials保持Leader与Active-Active前置条件.md)、[ADR-0193](ADR-0193-第一方插件边界与Capability契约版本.md)

## 背景

开发态仍有插件把运行状态直接写入本机 JSON 文件。现有 `state.shared.v1` 已统一身份派生、CAS 和错误语义，但生产默认 Provider 是 NATS KV，SQL Provider 尚未实现。与此同时，Database Runtime 只有参数化 SQL 和事务契约，插件仍需重复编写数据类型、Repository 和迁移代码。

## 决策

1. 种子服务采用两阶段启动。Bootstrap 阶段只启动 Seed Access、最小认证授权链、静态 Portal 必需模块和 Database Runtime；SQL Shared State 就绪后才启动依赖平台状态的完整组合。
2. Database Runtime 内部增加 SQL Shared State、Record Store 和 Schema Controller 模块，不建立新的运行插件。Backend Kernel 只保留可绑定的 Shared State Store SPI 和分阶段启动机制。
3. 平台控制数据库使用保留的 `PlatformControlStoreProfile`。非敏感配置保存在受保护的本机 Bootstrap Profile；Linux 生产秘密使用 systemd credential，开发允许 0600 文件。Seed verifier、恢复根和控制库自身解密根不得写入控制数据库。
4. SQL 是种子生产默认 Shared State Provider；NATS KV 保持可选协议；File 仅用于单测、未初始化开发环境和明确的 Seed/Recovery 根状态。Provider 不可用时 fail-closed，禁止回退文件形成双真相源。
5. PostgreSQL 和 MySQL 同批支持。平台控制数据使用独立逻辑数据库或独立 schema；普通插件必须通过 Connection Manager 获得业务 `connectionRef`，不能选择保留控制库连接。
6. 数据能力严格分为 `DataModel -> Repository -> Application Workflow`。DataModel 不声明页面、权限和业务动作；Repository 不含业务规则；所有对外操作即使只有简单 CRUD 也必须经过显式 Workflow。
7. `data.model.v1` 是语言中立签名契约。Go 工具在构建期验证模型并为插件实际语言生成 Go、TypeScript 或 Python 强类型 Repository 源码；生成物按模型分文件提交，CI 复生成检查漂移。
8. 安全增量 Schema 变化可自动执行；删除、改类型、收窄约束和数据重写必须使用签名迁移、备份前置检查、单一 Schema Controller 和持久迁移账本。
9. 数据库访问逻辑集中于统一 Database Runtime 契约，物理上 active-active 多副本运行。各实例维护本地池，普通调用本地优先并允许远端故障转移；事务保持实例亲和；Schema 迁移单写。

## 影响

- 种子运行状态可以由企业数据库备份、复制和恢复；
- 普通服务不持有数据库驱动、密码或独立连接池；
- 插件只需声明数据模型即可获得类型安全的数据读写层，但不能绕过业务流程；
- 当前开发状态不迁移，允许清理后重新初始化；未来生产迁移必须另走签名迁移和恢复流程。

## 实施记录

- 2026-08-05：P2 建立 `data.model.v1` 严格 Schema、Go 校验器和 Go/TypeScript/Python 确定性生成器；Manifest 使用外部路径与 SHA-256 绑定模型，架构门禁复生成已提交 Repository 并检查零漂移。首个真实模型由 Database Connection Manager 提供。Record Store、Schema Controller 和 SQL Shared State 尚属于后续 P3，不能把类型生成误记为持久化迁移完成。
- 2026-08-05：P3a 冻结 `record.store.v1` 请求边界和 Database Runtime 内部 Record Store 模块。模型目录按 generation 原子替换并复核 owner、模型身份和 SHA-256；SQL 只由 PostgreSQL/MySQL 方言编译器从白名单字段生成，tenant/service scope 由可信调用上下文注入。Schema 分类器仅自动接受建表、可空字段和非唯一索引，其他变化返回 manual。执行 capability、幂等账本、迁移单写和 SQL Shared State 未完成前不对外宣称 Record Store Ready。
- 2026-08-05：P3b 已实现 Database Runtime 内部 Record Store 执行面，包括 CRUD、受限 List、Batch、实例亲和 UnitOfWork、幂等账本和事务内 Outbox；Schema Controller 使用数据库 advisory lock、持久 migration ledger 和 SYSTEM/credential evidence 约束自动安全迁移；SQL Shared State 已按现有 `sharedstate.Store` 的 1 MiB、CAS、分页、作用域隔离和 fail-closed 语义实现 PostgreSQL/MySQL 模块。`data.model.v1` 提升到 `1.1.0`，索引字符串必须声明 `maxLength`，TypeScript `int64` 固定生成为 `string`，避免 MySQL 索引越界与 JavaScript 精度漂移。Record Store 和 SQL Shared State 仍未写入公开 Manifest 或主入口：P4 注入保留控制库会话、P6 完成多副本目录同步后才能宣称 capability Ready。破坏性签名迁移包仍属于 P3 后续检查点。
- 2026-08-05：P3c 增加 `data.migration.v1` 和 Manifest `backend.dataMigrations[]`。迁移文件的 SHA-256 由已签名插件 Manifest 固定，可信宿主同步时还必须投影已验证 Plugin Inventory digest 与 Artifact SHA；Runtime 原子校验模型和迁移来自同一制品。破坏性迁移显式声明备份、审批和可安全重试，SQL 限定为无注释、无分号的单条受限语句且不能修改 Runtime 内部表；执行时还必须同时持有连接 leader、备份完成和审批完成三类 service evidence。迁移账本记录成功迁移 ID，同一目标模型重放直接返回 Ready。P3 实现面已闭合；本机 Docker daemon 在真实 PostgreSQL/MySQL 矩阵准备阶段无响应，因此该矩阵仍列为环境阻塞，不能记为已通过。
- 2026-08-05：P4a 建立 `PlatformControlStoreProfile` 严格契约、owner-only generation CAS 文件 Store、systemd credential 与开发 owner-file 两种 `SecretSource`、`Test -> Initialize -> Commit -> Bind` Controller，以及只能向前切换、未绑定即 fail-closed 的 `sharedstate.BindingStore`。首次失败不提交 Profile、不绑定本地 JSON；替换候选失败保留旧 Ready generation；已绑定外部 Provider 故障时禁止回退文件。Database Runtime 远端适配、Bootstrap Tier 和配置 UI 仍属于 P4 后续。
- 2026-08-05：P4b 在 Database Runtime 内部增加 `platformcontrolbootstrap` 适配器，复用 PostgreSQL/MySQL Provider Registry、本地池和 pinned session 完成 Test、迁移锁、限定 schema 建表、Open/Probe 与 SQL Shared State 装配。适配器只返回可关闭的 `ManagedStore`，Profile 提交或绑定失败会立即释放候选池；TLS 增加校验证书链但不校验主机名的 `verify-ca`。`Bootstrapper/ManagedStore/SecretSource` 位于中立 Library，插件与 Kernel 都不反向依赖对方实现。该能力仍是 Database Runtime 内部模块，不新增插件，也不允许 Kernel 引入数据库驱动。公开 Database Runtime Capability 提升至 `1.2.0`，插件提升至 `0.9.0`。
- 2026-08-05：P4c 完成独立进程边界：Database Runtime 贡献仅固定 SYSTEM caller 可用的 SQL Bootstrap 与 Shared State Capability，宿主以 `RemoteBootstrapper/RemoteStore` 重新适配稳定 Store SPI。Deployment/Assignment 新增默认 `full` 的 `startup_tier`，Node Agent 在 Store Ready 前只激活显式 Bootstrap 单元；Controller 订阅可信能力目录 topology change 幂等恢复，不增加轮询。多副本逐实例打开尚未进入 P6，因此种子 Runtime 暂时固定单副本。
- 2026-08-05：P4d 把配置面接入同一两阶段协议。Controller 的 `Status / TestCandidate / Configure` 通过受限 Kernel Service 只开放给 Connection Manager；Portal 只能经 Management Binding、角色权限和 CSRF 保护的固定 BFF 路由调用。测试候选不执行初始化或提交，配置候选继续遵守 Test、Initialize、Profile CAS 和 Bind 顺序。平台控制数据库页面属于现有数据库全栈插件，使用 Workbench Form Page 且只提交 systemd credential name 或 owner-only 文件引用，不引入密码明文或新的普通应用插件。
- 2026-08-05：P5 第一批把 Connection Manager 的本机 JSON 真相源迁移为按租户 Shared State CAS。持久化协议在插件组合入口固定，所有正常管理 Workflow 先加载当前 Store revision，再以 leader-fenced create/update 推进连接定义、凭证候选、Runtime publication outbox 与回收队列；不可用或冲突均 fail-closed。Platform Control 的状态、测试和配置操作继续绕过该业务状态协议，只进入受限内核端口，避免 Bootstrap 循环依赖。当前聚合保留 Saga 原子边界；DataModel 生成的独立 Repository 将用于后续拆出的记录数据，不能机械拆散凭证与发布事务。
- 2026-08-05：P6 连接预算不再使用每实例固定上限。Database Runtime 启动组合根从 `clusterMaxOpen + maxReplicas` 一次派生每实例 ManagerPolicy；Pool Manager 原有的 generation 预算同时统计活动代、排空代和关闭失败保守占额，因此 active-active 扩容与双代滚动升级的最坏物理连接总量不超过集群硬上限。配置不足以为每个副本保留两个 generation 时拒绝启动，副本之间不共享 socket，也不在运行中借用连接额度。
