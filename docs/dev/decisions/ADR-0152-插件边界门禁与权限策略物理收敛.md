# ADR-0152 插件边界门禁与权限策略物理收敛

- 状态：已采纳，已实施
- 日期：2026-07-25
- 关联：[ADR-0001](ADR-0001-插件运行模型.md)、[ADR-0021](ADR-0021-权限判定强制点.md)、[ADR-0051](ADR-0051-Backend混合插件运行与受控内嵌边界.md)、[ADR-0089](ADR-0089-Runtime-Provider与共享Host池.md)、[ADR-0104](ADR-0104-Frontend-Runtime-Engine与React单实现.md)、[ADR-0150](ADR-0150-插件共享代码与能力复用边界.md)

## 背景

Foundation 与紧贴内核的平台插件审计发现，系统的主要问题不是插件总数，而是把逻辑贡献、签名交付单元和物理运行单元混为一谈：

1. React Runtime Engine 的浏览器入口只导出身份与能力元数据，Browser Root/Hydration 仍由 Portal Kernel 实现；进一步核对后确认同一制品还拥有真实的 Node SSR Runtime、Server Module Graph 和 Worker Generation 生命周期，因此不能把整个制品误判为纯空壳；
2. 每个 Backend 服务均启动 Authorization Enforcer，多数服务又启动 Platform Admin Access Policy，Portal 与 Interaction 再各自启动无状态 Checker，导致一条策略一个进程；
3. Node/Python Runtime Hello 只被 E2E 使用，却进入生产 Foundation 插件目录；
4. Native Authorization Engine 是真实 Provider，但主要实现位于 SDK；
5. Role Management 前端与 Authorization Policy 后端属于同一业务能力，却拥有不同插件身份和版本。

继续按“所有东西都是独立插件”的表面一致性扩张，会增加进程、制品版本、组合引用、启动依赖和 Resolver 特例，同时削弱真实边界的可理解性。

## 决策

### 1. 插件资格门禁

独立插件必须至少拥有下列一个真实边界：

- 独立替换或发布版本；
- 在线配置；
- 状态、凭证或外部系统适配；
- 独立故障/安全隔离；
- 集群生命周期；
- 内容寻址和按需下载。

不满足条件的代码归入 Contracts、SDK、Library、现有插件内部模块或测试 Fixture。代码量和文件数量不作为插件资格。

### 2. 权限逻辑与物理进程分离

每个 Backend 服务保留一个本地、fail-closed 的 Authorization Enforcer 运行单元。Platform、Portal 与 Interaction 的无状态 workload 策略作为 Enforcer 制品内部的独立 Policy Bundle 模块交付，保持各自 ID、优先级和测试，但不再各自启动进程。

当前 Bundle 与 Enforcer 同属一个已签名制品，避免在尚无独立在线发布需求时引入新的策略制品协议。未来只有出现独立审批、独立版本或第三方策略来源时，才把 Bundle 提升为独立签名数据制品；数据制品不得自动获得进程。

Bootstrap Policy 暂时保留独立运行单元。它处于设置服务启动前的自举链，并承担 dynamic-go Runtime 的真实生产验证；只有 Enforcer 能在无远端 Policy Snapshot 时可靠加载、验证和回退自举 Bundle 后，才允许物理合并。

### 3. Capability Grant Plan

插件到宿主的结构授权由可信宿主从已验证 Manifest、发布者策略上限和 Platform Profile 编译为不可变 `CapabilityGrantPlan`。内核拥有“编译、校验、裁剪和执行 Grant”的机制，插件与在线授权系统拥有策略内容。

第一阶段把既有 `capabilities.kernelServices` 编译为显式 Grant Plan，并保持 HostCall 前置拒绝。后续新增跨插件 capability grant 时必须使用同一计划，不得继续在 workload 策略中按插件 ID 扩张硬编码白名单。

用户、角色、租户和对象级授权不进入 Grant Plan，继续由签名 Permission Catalog、Policy Snapshot、Authorization Enforcer 和目标服务对象级校验完成。

### 4. 全栈制品与代码归属

- Role Management 前端并入 `cn.vastplan.platform.security.authorization-policy`，形成一个全栈插件；前后端源码仍分包。
- Native Authorization Engine 的 Provider 实现移回其插件目录；只有无权限、确定性的求值算法可以进入 Library，SDK 不再拥有具体 Engine。
- Runtime Hello 插件移入 E2E Fixture，退出生产 Foundation 命名空间。

### 5. Frontend Runtime Engine

`cn.vastplan.foundation.frontend.runtime.engine.react` 继续保留独立制品，因为它实际拥有 Node SSR Runtime、Server Module Graph 物化、Worker Generation 和独立服务端升级/故障边界，满足插件资格。浏览器入口当前只是同一签名制品内的 family/contract 兼容描述；Browser Root、Hydration 与 React 组件树仍属于当前 React Portal Kernel，不宣称已经可由该入口完整替换。

当前不为了形式统一搬运 Browser Root。只有第二个 Browser Engine 出现明确需求时，才升级 Browser Engine Bridge，并要求候选实现真正接管 Root、Hydration、Generation 和框架单例生命周期。届时 Portal Kernel 不得继续直接绑定 `react-dom/client`。文档、清单和产品界面必须分别标注“Browser compatibility descriptor”与“Server Runtime Provider”，避免把元数据入口描述成完整浏览器引擎。

### 6. 产品分类不等于运行单元

Renderer、Shell Library 等独立签名、按需下载模块继续保留独立制品，但产品层分类为 Foundation Library，不向用户暴露为普通 Application 插件。Catalog 可以很小，只要它实际拥有允许集合、摘要锁和选择治理；不得仅凭代码行数合并其下载与故障边界。

## 实施顺序

1. 固化项目开发门禁并迁移测试 Fixture；
2. 合并 Authorization Policy 全栈制品，修正 Native Engine 代码归属；
3. 把 Platform/Portal/Interaction Checker 收敛到 Enforcer Policy Bundle，并把组合器的具体权限插件特例泛化为 host-local 拓扑规则；
4. 引入不可变 Capability Grant Plan 并迁移结构授权；
5. 校正 React Runtime Engine 的 Browser Descriptor 与 Server Runtime Provider 职责说明；
6. 更新 Profile、构建清单、文档与架构测试。

## 影响

- 同一 Backend 服务不再为每条无状态权限规则启动独立进程；
- 逻辑策略仍可独立测试和按优先级组合；
- 内核只增加通用 Grant 机制，不吸收平台业务策略；
- Foundation 插件目录不再包含仅用于验证 Runtime 的生产假象；
- 同一业务能力的前后端版本保持一致；
- 新增插件需要说明真实替换或隔离边界，Resolver 特例会成为强制复审信号。
