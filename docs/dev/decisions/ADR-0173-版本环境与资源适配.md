# ADR-0173 版本环境与资源适配

- 状态：已采纳，P2.2 Workspace Manager 与 JSON Snapshot Adapter 已实施
- 日期：2026-07-30
- 关联：[ADR-0172](ADR-0172-通用版本账本与可插拔存储Provider.md)、[ADR-0095](ADR-0095-Database-Runtime多Provider连接池与集群事务.md)、[ADR-0123](ADR-0123-插件共享状态与可信Provider.md)

## 背景

Version Ledger 已具备不可变版本、Head、Tag、diff 和 DAG，但 API-only 模型会迫使每个插件重复处理 Session、Lease、基线、幂等和 Head CAS。如果 Portal 只保存 VersionRef 并在读取时装配全部历史，还会产生 N+1 调用、Ledger 故障放大和 active-active 实例重复加载。另一方面，把所有资源都实现成真实 Git checkout 会让在线配置承担不必要的进程、磁盘和同步开销。

## 决策

1. 在 Ledger 上增加中立的 `version.workspace.v1`，统一有 Lease 的 open/read/write/changes/commit/discard/renew 会话；业务功能不直接选择 Provider。
2. 增加 `version.resource.v1`，由受信 Environment Profile 把 ResourceType 映射到 namespace、Adapter、允许模式、默认模式、投影策略和配额。
3. 运行模式分为 `snapshot / overlay / git`。Snapshot 是 JSON 在线功能默认值；Overlay 使用写时复制和懒物化；Git 只能显式启用。JSON Adapter 不得声明 Git 模式。
4. Workspace Manager 每服务宿主共享，不为每个 Session 或插件启动进程。第三方隔离、原生库冲突或企业策略才允许 Adapter 使用独立进程。
5. 领域插件保留业务状态与有限热投影。历史内容由 Ledger 保存，当前 Draft/Release 和运行时物化结果留在领域热路径；禁止启动或列表时装配全部历史。
6. 精确 VersionRef 内容允许进入有界 LRU；不可变对象无需失效广播。缓存、投影都必须通过 contentDigest 复核，不能成为第二真相源。
7. Environment Profile 和 Session 不包含 Provider、endpoint 或凭证。Session 绑定精确 Profile digest、tenant、resource、actor、base Ref 和 Head revision。
8. 数据库有双重角色：Relational Provider 可保存 Ledger 数据；数据库连接定义和 Schema 可通过 Resource Adapter 被版本化。Database Runtime 继续独占连接池和秘密 Material Lease。
9. 高频事务、日志、指标、队列和秘密不进入 Workspace；秘密只保存 CredentialRef，大文件只保存内容寻址清单或 ArtifactRef。

## 否决方案

- **所有领域只保存 VersionRef，读取时全量 hydrate**：读放大、故障耦合和 N+1 不可接受，否决。
- **业务插件各自封装 Ledger API**：Session、CAS 和安全规则必然漂移，否决。
- **所有资源都使用真实 Git 工作区**：在线配置开销过高，否决。
- **Workspace 配置直接指定数据库或 Provider**：破坏受信路由和秘密边界，否决。
- **把领域审批和上线放进 Workspace**：形成万能状态机，否决。

## 实施顺序

1. P2.1（已完成）：Resource/Workspace 契约、JSON Schema、Go 校验和 Ledger/Workspace Go SDK。
2. P2.2（已完成）：实现 Go Workspace Manager、内存 Snapshot Session、Lease/配额、JSON Adapter 和 Memory/Ledger 契约测试。
3. P2.3：Portal 以 Workspace 接入，保留当前 Draft 与 Release 热投影，历史按需读取并覆盖故障注入。
4. P2.4：实现 Overlay File Adapter、对象清单和 Runner/Agent 文件工作区。
5. P2.5：按真实需求实现 Git Adapter/Provider 与 Python、Node SDK。
6. P3：Relational Provider 和数据库连接/Schema Adapter，验证多数据库方言和 active-active。

## 影响

正面：任何获授权功能可通过环境使用统一版本语义；在线热路径不依赖历史装配；Snapshot 默认避免 Git 开销；数据库存储与数据库资源语义分离；多语言只需实现 SDK。

代价：增加 Workspace Manager 和 Adapter 生命周期；写入包含 Ledger commit 与领域 CAS；Overlay/Git 需要 Lease 清理、配额与磁盘治理；领域插件必须明确哪些数据是热投影、哪些是历史真相。

## P2.2 实施约束

- Workspace 插件采用 `leader / leader-owned`。Session 是有界临时编辑状态，Leader 重启后未提交 Session 丢失；不可变版本和 Head 仍以 Ledger 为唯一事实源。
- Session 在打开时固定 Environment digest、Binding、Adapter 实例、大小与 Lease 上限。后续在线更新 Profile 时不得让既有 Session 静默继承新配置。
- Session 由可信 `tenant + actor` 所有，跨 actor 查询按不存在处理；写入、续租、丢弃与提交都使用 Session revision CAS。
- 提交先用可信领域持久化并传入的稳定 `operationId` 写 Ledger，再创建或 CAS 移动 Head。该身份必须跨 Session/Leader 重建；Head 写响应不确定时必须 read-after-error；Head 已被他人移动时允许留下不可达版本，但不得覆盖新 Head，Session 保留为 Dirty 供调用方重开或处理冲突。
- P2.2 只内置 `version.resource.json.v1`，支持 `snapshot`。它规范化 JSON object、生成确定性变化路径，并拒绝敏感字段中的明文 material；秘密只能以合法 `ManagedCredentialRef` 表示。
