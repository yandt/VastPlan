# ADR-0167：三级组件尺寸与组合密度投影

- 状态：已接受
- 日期：2026-07-28

## 背景

Portal 基础组件曾同时使用 `regular/compact`、`sm/md/lg` 和 `compact/standard/comfortable`。同一个“紧凑”意图需要在 Workbench、Ant Design、Arco 和 MUI 中重复设置像素，导致视觉调整难以一次贯通；同时，尺寸还被错误地用来暗示导航或操作等组件用途。

## 决策

1. UI Contract 7.0 提供唯一 `ComponentSize = sm | md | lg`。Button、IconButton、Select、Menu、Tabs、Pagination 和 FormRenderer 使用该尺寸语言，默认值为 `md`。
2. `CollectionDensity = compact | standard | comfortable` 保留为组合组件及用户偏好语义，并由 Workbench 固定投影为 `sm | md | lg`。功能插件不能为集合内部每个控件逐项指定尺寸。
3. 组件尺寸的可执行数值只保存在 `componentSizeRecipes`；Ant Design、Arco、MUI Renderer 映射本框架原生 size，并用 recipe 补齐框架间差异。
4. 尺寸只控制几何。Menu 的 `navigation/action`、Button 的 `kind`、动作的 `tone` 等用途和状态继续使用独立属性。小号导航菜单不会因此变成操作菜单。
5. Page、Shell、Grid、Stack 等结构组件不机械增加 size；Dialog、Drawer 和 SplitView 的 `sm/md/lg` 继续表示宽度，并使用 `width`/`primaryWidth` 命名。
6. 这是破坏性 UI SDK 变更，不保留 `regular/compact` 别名；所有第一方 Frontend Foundation 与功能视图同步声明 `frontend.ui ^7.0.0`。

## 结果

- 调整某一级尺寸时只修改共享 recipe，三个 Renderer 和 Workbench 组合面同时生效。
- 用户仍通过集合“显示密度”选择紧凑、标准或宽松，不接触组件实现细节。
- 新组件必须先判断尺寸是否具有清晰几何含义；不能用 size 替代 variant、tone、layout 或 width。
