# ADR-0158 应用插件兼容范围与精确运行锁

- 状态：已采纳并实施
- 日期：2026-07-26
- 关联：[ADR-0017](ADR-0017-版本定义与兼容性机制.md)、[ADR-0098](ADR-0098-制品依赖解析锁与离线Bundle.md)、[ADR-0143](ADR-0143-插件化应用意图规划与派生依赖.md)

## 背景

Application Intent 原先要求根插件使用精确制品引用。该规则保证运行稳定，却把“用户允许哪些版本”和“当前实际运行哪个版本”混成一个概念：每次兼容补丁都要人工修改所有服务，多个服务对同一插件的要求也无法在规划阶段求交集。

系统仍必须满足不可变发布、可复现部署、重启不漂移、历史回滚和垃圾回收引用保护。因此不能把 SemVer 范围直接带入 Deployment、Assignment 或运行时，也不能在启动时重新求解。

Feature 还会随候选版本改变可选依赖。若先固定 Feature 依赖再选择候选，可能错误拒绝本可通过回溯解决的组合；若没有复杂度边界，恶意或异常目录又可能放大求解成本。

## 决策

### 1. 分离期望范围与精确运行锁

Backend Application Intent 的根插件直接使用共享 `ArtifactRequirement`：`pluginId + constraint + channel + features`。管理界面只提供两种策略：

- 固定版本：`=x.y.z`；
- 兼容升级：`^x.y.z`，遵循 npm caret 的 SemVer 边界，特别是 `^0.4.0 <0.5.0`、`^0.0.5 <0.0.6`。

Intent 不开放任意约束编辑器、通配符、预发布范围或逻辑组合。Manifest 传递依赖和 Planner 内部聚合仍可使用完整 SemVer 表达式，因为它们属于开发者契约和受信求解过程。

Repository 在显式规划动作中将范围解析为精确 `ArtifactLock`。Application Composition 可以保留规划输入表达，Kernel Resolver 输出的 Deployment 与 Scheduler 输出的 Assignment 必须保存 `pluginId + version + channel + sha256`；Activation、Seed/LKG、回滚和 GC 引用同样保存不可变精确 ref 与摘要。普通启动不得重新求解或发布。

### 2. 一个组合中同一插件只有一个版本和通道

Planner 对多个内核服务的根约束及传递依赖求交集；同一插件最终只允许一个精确版本和通道。Feature 按服务声明，在全局候选选择时取并集以保证锁包含所有必需包；生成各 service 闭包时仍按服务隔离，不能把一个服务启用的 Feature 泄漏到另一个服务。

同一插件的显式 channel 冲突直接返回错误，不进行隐式优先级选择。

### 3. Feature 随候选参与回溯

Resolver 选择候选后，才读取该候选签名 Manifest 中对应 Feature 的包依赖和 runtime requirement。候选缺少 Feature、依赖不相容、能力不满足或形成环时，求解器继续回溯其他合法候选；全部失败后返回稳定诊断。

Artifact Lock 保存最终候选的有效依赖闭包和根 Feature 选择，Planner 再按精确 Manifest 生成服务级闭包与运行时绑定。

### 4. 确定性和复杂度上限

Resolver 预编译约束，优先选择剩余候选最少的未决插件，并使用稳定排序。每次解析具有确定性的候选评估预算；超过预算返回 `RESOLUTION_COMPLEXITY_LIMIT`，不返回部分锁，也不退化为不受限搜索。

### 5. 升级必须显式触发

Catalog 新版本只会使现有草稿计划 stale。用户刷新计划后才能看到新的精确候选；提交、审批和发布继续绑定新 `planDigest`。已发布服务不会因为仓库出现新版本而漂移，回滚仍从历史 Intent 生成新的单调 revision 并重新经过规划与审批。

## 备选方案

### 所有层都使用精确版本

最简单，但兼容补丁升级需要重复编辑大量服务，无法表达最低兼容版本；拒绝。

### 把范围直接交给 Node Agent

可以在启动时自动选新版本，但会破坏可复现部署、离线恢复、审批摘要和回滚；拒绝。

### 完全复制 npm/Python 的开放式输入

生态表达力强，但普通平台用户需要理解复杂约束，通配符和组合范围也会扩大误配置与求解攻击面；应用输入拒绝，开发者 Manifest 仍保留完整 SemVer。

### 每个服务独立选择同一插件版本

隔离直观，但同一 Application Composition 会出现多版本身份、能力寻址和共享运行时歧义；拒绝。确有不兼容要求时拆分组合或故障域。

## 影响

正面：兼容升级不再要求逐服务修改版本；运行层仍完全精确、可复现；Feature 和多服务约束可正确回溯；恶意依赖图受确定性预算保护。

代价：Repository Resolver 和 Planner 需要维护候选级 Feature 求解、约束聚合与更完整的冲突诊断；范围刷新可能产生需要人工确认的新候选。

边界：本次只开放 Backend Application Intent。Frontend、Desktop、Mobile 若采用范围输入，必须分别新增适合其发布模型的决策与契约；不得直接把 Backend 输入复制到其他内核。

## 实施记录

- 2026-08-08：Backend Kernel Resolver 将 Application Composition 中非空 SHA-256 视为 Planner/Artifact Lock 已生成的精确锁，必须与制品源返回的已验证摘要一致；只有不携带摘要的受信 Profile/Seed 输入才由 Resolver 产生新锁。一次发布预览对每个规范化 ref 只读取一次，Artifact Reference、Configuration Catalog 与 DataModel 投影复用同一制品快照；host-local 拓扑判断只消费该快照中已验证的 Manifest。
