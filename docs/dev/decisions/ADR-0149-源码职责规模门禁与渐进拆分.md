# ADR-0149 源码职责规模门禁与渐进拆分

- 状态：已采纳并实施
- 日期：2026-07-25
- 关联：[代码目录结构](../guides/代码目录结构.md)、[工程规范](../guides/工程规范.md)

## 背景

项目已经按内核、插件、契约和 SDK 建立宏观边界，但局部文件仍会在连续功能迭代中吸收入口适配、应用工作流、状态持久化、外部端口和协议分发。单纯按总行数拆文件会破坏内聚；完全不设门禁又会让职责集中只能依赖人工复查。

本次检查发现手写生产源码中有 22 个文件超过 600 行，若干 Go 函数超过一个可完整评审的工作流规模。与此同时，Protobuf 生成物、测试、纯锁文件和少量公共契约天然较长，不能使用无例外的机械限制。

## 决策

1. 手写生产源码默认不超过 600 行。Go、TypeScript/TSX、JavaScript、Python 和 Shell 纳入；生成的 `*.pb.go`、测试和派生目录排除。
2. Go 函数默认不超过 160 行，以 AST 的真实函数起止位置计算，不使用相邻声明间距估算。
3. 既有超限对象进入显式 burn-down 例外表。每条例外必须写明拆分原因，并把当前行数冻结为上限；继续增长立即失败。
4. 超限对象降到默认阈值后，例外本身变成测试失败，要求同步删除，避免永久白名单。
5. 阈值只是阻止职责继续集中，不代替设计判断。拆分继续以领域、工作流、端口、适配器和依赖方向为依据；禁止通过压缩格式、合并语句或移动到通用 `utils` 绕过门禁。
6. 架构测试不得扫描 `.vastplan`、`dist`、`node_modules`、`graphify-out` 等派生目录，防止把已安装制品或本地运行快照误判为源码。

## 首批拆分

- Platformdev 将制品、Fixture、网关、Portal 发布和本地身份从主编排器分离；
- Database Connection Manager 将进程入口、持久模型、端口、Saga、定义用例和协议分发分离；
- Node Agent 将候选 Apply 拆为准备、插件启动、迁移、所有权、路由、提交和回滚事务，并把领导权、迁移、监控和注册分文件；
- Deployment Scheduler 将规划、资源、放置、Generation 和 Controller 分离，`Reconcile` 只编排阶段；
- TypeScript Platform Admin SDK 将公共类型、Client 实现和稳定根导出分离。

## P1 渐进拆分

- 制品仓库运行时保留 `Manager` 作为状态与依赖组合根，将制品发布/读取用例和卷迁移工作流分别迁入 `artifact_operations.go`、`migration.go`；
- Catalog 保留查询模型与内存索引门面，将 Journal 恢复/快照持久化和制品条目解析/验证分别迁入 `persistence.go`、`entry.go`；
- Go 插件 SDK 将会话建立、通道分发、生命周期、宿主回调和动态贡献更新从稳定入口分离；
- ProtocolBus Client 将进程启动、能力调用与 HostCall 分离，Addressing Router 将本地/远端调用、事件与目录读取、关闭/目录观察分离；
- Node Agent Runtime Pool 将托管策略与共享类型、Runtime Host 进程控制、池租约管理分离；
- Deployment Manager 将共享状态、节点/引导工作流与协议适配分离；Credentials 将 Vault Transit、共享状态、托管凭证/material lease、传统记录与协议适配分离；
- Database Pool Manager 将连接代际生命周期、租约与调用方并发闸门、回收/预算/诊断分离；
- Interaction Broker 将持久状态、交互生命周期、动态表单安全验证与防御性复制分离；
- 拆分保持原包名、公开类型和方法签名不变，不引入跨包兼容层；对应的规模门禁例外在同次改动中删除。

## P2 渐进拆分

- Plugin Manifest 契约按稳定模型、贡献解析、运行时策略、Schema 编译/解析、清单规则和 descriptor 校验拆分；
- Platform Admin API 按基础设置/数据库、制品、部署和服务端口拆分 DTO；
- Frontend Composition 契约按稳定模型、Schema 编译、Renderer/Shell 校验和门户组合/目录校验拆分；
- Backend HostFactory 按组合根、Shared State、平台服务和节点服务拆分；Node Reconciler 按主编排、目标收敛、实际态维护和安装/校验支持拆分；
- ProtocolBus Server 按握手、Channel/贡献注册、生命周期和插件消息分发拆分；Addressing Registration 按准备、激活/调用和租约/关闭拆分；
- Deployment Test Release 按申请/引用、执行/回滚和制品/绑定校验拆分；制品 Resolver 按请求过滤、约束求解和锁生成/验证拆分；
- 仓库 Publications 按审批状态机、发布授权、供应链证据和快照持久化拆分；
- TypeScript UI Primitives 保留稳定根导出，将表单、基础组件、Renderer、Portal Runtime/Workbench 和 Shell 契约分文件；
- `platform-dev.sh` 保留命令解析与生命周期编排，将进程/构建/就绪支持和显式插件开发工作流迁入只可被 source 的职责文件；当前没有必要为规模门禁把已清晰的 Shell 行为强行迁入 Go。

## P3 长工作流拆分

- ControlPlane `Run` 将 Flag 绑定与默认 Controller 身份生成迁出，入口继续拥有 NATS、发布和 Controller Fleet 的顺序；
- Backend reconcile 将参数绑定、参数规范化/交叉校验、启动输入准备、Runtime 依赖装配、凭证/部署服务装配和 Reconciler 创建分离；
- 资源关闭的 `defer` 顺序仍由原入口持有，拆分不改变进程锁、控制面、Runtime、租约和 systemd 通知的生命周期语义。
- 制品仓库进程入口只保留配置、可信依赖、传输和 SDK 生命周期装配，协议 Handler 按读取/评估与生命周期/GC 两组构建；
- 离线 Bundle 创建把单制品供应链取证、报告归档和 Tar 写入抽成独立步骤，临时文件提交/回滚仍由顶层工作流负责。
- Portal Composer 协议分发按组合草稿、Platform Profile、Binding/Activation、Test Release 和发布治理拆分；
- API Exposure 用户分发按 Exposure、Data Plane、审计和 Gateway 兼容协议拆分，可信 Principal 投影仍只发生在原 Capability 边界。
- 契约拆分继续保持原包路径和导出标识不变，调用方不需要兼容迁移。

## P4 重复职责治理

- 公共抽取以“跨模块、语义稳定、无副作用”为准，不以函数短小为唯一依据，也不建立无边界的 `utils` 包；
- SHA-256、定长十六进制值和带前缀十六进制标识属于 Wire 契约的词法规则，统一放在 `contracts/schemas/common/v1`。大小写规则必须由不同方法显式表达，禁止在复用时悄悄放宽协议；
- 制品归档条目路径属于供应链信任边界，统一由 `artifacttrust.NormalizeArchivePath` 校验。ZIP、Tar 和插件安装不得各自维护近似实现；该校验同时拒绝 Unix 绝对路径、Windows 盘符、反斜杠绝对路径、NUL 和目录逃逸；
- 领域状态、权限、集合顺序、错误文案和协议事务校验继续留在所属包。它们即使只有数行，也不因表面代码相似而提升为公共方法；
- 严格 JSON 解码和安全随机令牌生成具有独立的错误语义或安全生命周期，后续如需统一，应分别建立明确契约，不能混入词法校验工具；
- 制品仓库的 Runtime Descriptor 与 Handler 集合建立双向契约测试，防止拆分后出现“已声明未注册”或“已注册未声明”的协议漂移。

## P5 过度拆分与控制流治理

- 短函数不以行数判错。公开契约、接口实现、跨平台适配、领域命名和安全策略包装允许保持极短；仅删除私有、低复用且不增加校验、转换、错误语义或稳定边界的转发函数；
- 插件打包 staging 不再通过逐层补空参数的函数阶梯模拟可选参数，统一使用具名 Options，避免 9–12 个同类型位置参数发生错位；
- 配置 Catalog、Deployment Contract、Runtime Host 响应和插件配置中断恢复按工作流阶段拆分，顶层函数只负责顺序与错误传播；
- HostFactory 先生成有序服务注册清单再统一注册。重构必须保持原有注册顺序，不把可选依赖的存在判断隐藏在反射或通用容器中；
- Portal Preference Handler 将 Activation 解析、请求构造和 Capability 错误映射分离；页面 Action 使用字典分发，不继续扩展 `if/else if` 路由；
- `CallContext` 字段投影等安全边界保持显式字段复制。安全代码的可审计性优先于控制流深度指标，不为降低数字引入反射或通用映射器；
- 嵌套深度和单语句函数扫描只作为人工复核线索，不直接作为 CI 失败条件。只有可证明无语义的转发层才进入强制门禁候选。

## 影响

新增职责会在本地和 CI 的 `go test ./engineering/arch` 中被及时拒绝。现存大文件不会被迫一次性重写，但不能继续增长；后续功能触及例外文件时应优先拆出本次相关职责。阈值变化必须更新本 ADR，而不能临时放宽测试绕过具体失败。
