# ADR-0192 插件最小升级与兼容影响解析

- 状态：已采纳，P0/P1/P2 与 P3 发布编排已实施
- 日期：2026-08-04
- 关联：[ADR-0017](ADR-0017-版本定义与兼容性机制.md)、[ADR-0098](ADR-0098-制品依赖解析锁与离线Bundle.md)、[ADR-0144](ADR-0144-组合服务代际热升级与插件动态调试.md)、[ADR-0157](ADR-0157-开发Seed-Runtime-LKG快照.md)、[ADR-0165](ADR-0165-Contract-Registry与插件发布编排.md)

## 背景

插件化的目标是让实现可以独立升级、组合和回滚。stable 制品的精确版本与 SHA-256 必须保持不可变，但此前兼容的公共 UI Contract minor 升级会重写全部 Portal Profile 范围；共享前端 SDK 改动也会使开发 HMR 重建全部插件。这把“内容变了”错误等同于“所有消费者接口都变了”。

## 决策

1. 保持两层事实：组合意图使用插件版本范围和能力约束；候选 Generation 与生产 Activation 只保存仓库解析出的精确 ref、包摘要与 Lock。运行节点永不解析 latest，也不得用范围替代已激活的精确锁。
2. 每个 Release Spec 必须把选中插件标为 `implementation`（默认）、`additive` 或 `breaking`。每种变更都会产生新的目标插件制品版本；前两者复用满足声明范围的消费者，`breaking` 必须把直接消费者加入同一 Release Spec 并重新验证。
3. Release Plan 输出 `impacts`：明确哪些消费者被复用、哪些必须随破坏性升级处理。反向依赖是影响分析输入，不是默认重建清单。
4. Contract Registry 只在 Profile 当前范围不再接受 canonical 契约版本时才推进该 Profile。兼容 minor 只更新生成常量和实际使用新能力的插件，不单独导致 Profile revision、摘要锁或 Activation 改变。
5. 开发态把 Portal 宿主源码与共享 SDK 源码分开监听。共享 SDK 的兼容更新只重建宿主和实际变更插件，复用已验证模块；宿主启动逻辑、模块格式或插件集合增删仍全量构建。任一契约校验失败时保持上一 Generation。
6. Backend、Frontend、Desktop、Mobile 共用 `PublicInterfaceFingerprint` 和规范化 `PublicInterfaceSurface`：它们从已签名 Manifest 的协议、Schema、能力、生命周期要求、依赖和贡献描述计算，并投影到每个新 Plugin Inventory 条目；版本号、构建路径、SBOM 和模块图字节不参与。接口事实不能从任意源码 AST 猜测。
7. P3 的 Release Plan 在组合根注入活动 Generation 的可信 Inventory 基线后，自动复核发布者声明：`implementation` 必须指纹不变；`additive` 必须满足“旧公开结构是新结构的子集”；更改或删除旧字段、对象属性、数组成员时必须声明 `breaking` 并完成直接消费者闭包。开发 CLI 只提供严格校验的文件适配器；生产发布控制器必须从活动 Generation 的 Inventory 端口注入该事实，不能相信调用方路径。旧 Inventory 因缺少公开接口描述而无法证明 `additive` 时，按失败关闭处理。将各类已激活服务的 Inventory 投影为该端口的正式实现，属于后续 P4。

## 后果

- 开发保存实现代码不再默认触发 stable 重建或所有前端模块重编译。
- stable 的不可变身份、签名、Supply Chain 准入、精确 Lock 和 Activation 原子切换不被削弱。
- 破坏性变更不允许仅靠错误的 patch 版本逃过影响分析；发布者必须显式声明并提交消费者的兼容更新。
- 旧 Inventory v1 没有该字段时保持可读；需要最小升级判定的新候选必须使用带指纹的 Inventory，不引入业务代码扫描或内核特例。
- `additive` 不再只是发布者的文字承诺：公共 JSON 结构的保留关系可被跨代重放与验证；协议层无法由通用结构推断的业务语义，仍必须由该协议的兼容测试覆盖。
