# ADR-0185：四级组件尺寸与组合根继承

- 状态：已接受
- 日期：2026-08-02
- 修订：[ADR-0167](ADR-0167-三级组件尺寸与组合密度投影.md) 与 [ADR-0168](ADR-0168-表格密度与内部控件尺寸隔离.md) 的尺寸部分

## 背景

三级 `sm / md / lg` 同时承担了“极紧凑操作控件”和“普通小号控件”两种意图。行操作、动作菜单、筛选表单等需要保持当前最小几何，而页面、Grid、Descriptions、BodySections 等组合根又缺少统一的尺寸继承，调用方只能逐组件重复配置。与此同时，Form 与 Overlay 曾把 `size` 同时解释为内容密度和弹窗宽度，导致契约难以扩展。

## 决策

1. UI Contract 9.0 定义唯一 `ComponentSize = xs | sm | md | lg` 和小接口 `SizeableProps { size?: ComponentSize }`；默认值统一为 `md`。
2. 原 `sm` 的极紧凑几何迁移到 `xs`，新增 `sm` 作为极紧凑与标准之间的档位。行操作、动作溢出菜单、筛选表单及拖拽/显隐图标显式使用 `xs`，避免视觉漂移。
3. `ComponentSizeProvider` 在组合根解析一次尺寸。Page、PortalShell、Panel、BodySections、Stack、Grid、GridItem、Workbench Page、Collection、Form、Overlay 与 Dashboard 可以覆盖尺寸；未覆盖的后代只读取上下文，不得各自重复写默认值分支。
4. `Page.size` 只控制正文 padding、标题与区域节奏，并向后代继承；页面宽度继续由 `bodyLayout` 控制。`Grid.size` 只决定未显式声明时的 gap 并向 GridItem 后代继承；列数和 span 继续由响应式列契约控制。
5. Table 的 `density` 仍只调整表格行高、表头与单元格留白，不得传播为 `ComponentSize`，也不得改变行操作按钮或图标尺寸。
6. 组件尺寸与 Overlay 几何分离。`FormWorkflow.dialogWidth` 与 `WorkbenchOverlayDefinition.width` 使用 `sm | md | lg`；`size` 只表达内容组件尺寸。旧的宽度语义不保留别名。
7. 所有可序列化 Workbench 定义在注册时统一校验 size，Renderer 仅通过 `componentSizeRecipes` 和框架映射落实可执行几何。功能插件不得传像素或框架私有 size。

## 备选方案

- 建立一个含所有视觉字段的 `BaseComponentProps`：继承方便，但会让不相关组件获得无意义属性，形成新的大接口，拒绝。
- 只给基础控件增加 `xs`：无法解决页面和组合组件的重复配置，也不能形成统一继承链，拒绝。
- 将 Table density 重新投影为组件尺寸：会再次使用户的表格偏好缩放整页与行操作，拒绝。

## 影响

- 常规页面无需声明即可得到 `md`；需要紧凑配置页时可在 Page 或 Workbench 组合根声明一次，后代自动继承。
- Page/Grid 的尺寸行为可预测且不污染宽度、列数或 Table density。
- UI Contract 主版本升级至 9.0，Foundation UI 插件、第一方功能插件、Catalog/Profile、测试夹具与 Runtime Generation 必须原子同步。
