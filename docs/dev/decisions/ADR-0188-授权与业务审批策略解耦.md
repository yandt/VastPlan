# ADR-0188 授权与业务审批策略解耦

- 状态：已采纳，Portal 首个接入已实施
- 日期：2026-08-02
- 关联：[ADR-0107](ADR-0107-插件权限目录与系统管理授权治理.md)、[ADR-0187](ADR-0187-认证会话授权四域解耦与快照交付.md)

## 背景

权限检查只能回答“当前主体是否拥有执行审批操作的资格”，不能回答“该主体是否可以审批这一份由谁提交、冻结摘要是什么、是否完成复验的业务对象”。Portal Composer 原先把异人规则硬编码在状态机内，又把拒绝统一映射成 `permission.denied`。结果是 Seed Owner 明明拥有 `platform.portal.approve`，仍在审批自己提交的 Publication 时得到无法解释的 `forbidden`；前端也无法提前显示真实审批要求。

## 决策

新增框架无关 `approval.policy.v1`，固定拆分三项责任：

1. Authorization Enforcer 只验证 Manifest 声明的权限，例如 `platform.portal.approve`。
2. Approval Policy 只根据可信主体、提交人、资源身份、冻结摘要和复验证据返回 `allowed/review-required/denied`，不签发 Session、不读取 Role Store。
3. Portal Composer 仍是对象状态、摘要 CAS、审批结果和审计记录的最终强制点；前端传入的布尔值不能替代服务端复核。

首版提供两个真实 Adapter：

- `different-subject`：提交人永远不能审批自己的候选；用于企业生产 Profile。
- `single-operator-review`：不同主体可直接审批；同一主体必须重新提交精确冻结摘要、明确确认和 4 至 512 字符审计原因。它明确记录为单人复验，不伪装成异人审批；用于尚未接入企业身份的 Seed Profile。

具体实现只在可信组合根根据 service-scoped Profile 选择一次，并以 `ApprovalPolicy` 接口注入。后续工作流和领域服务不得读取 development/production 字符串自行分支。Manifest `operationGuards[].approval=policy` 只表示该操作由注入策略决定，不能作为允许结论。

Portal 治理读模型投影当前主体对应的审批决定。Workbench 只根据该服务端投影显示“策略允许”“需单人复验”或“需其他审批人”，并继续声明 `platform.portal.approve`；实际提交仍由后端重复执行同一策略。

## 语言与物理边界

契约和内置确定性策略使用 Go：判断无网络、无大生态依赖，Go 与现有 Portal Composer 状态机、测试和资源模型最匹配。Workbench 表单适配使用 TypeScript。首版不创建独立进程或空壳插件；两个无状态、同信任域策略作为同一 Library 的 Adapter。未来外部审批系统需要独立凭证、网络、状态或故障隔离时，可在同一 wire contract 后增加 RPC Provider，而不修改领域工作流。

## 安全边界

- 单人复验不是 MFA，也不是第二个人；页面和审计必须使用准确名称。
- 浏览器只能提交 ReviewEvidence；Portal Host 固定资源 ID，领域服务重新读取当前冻结摘要。
- 摘要变化、未确认、原因缺失、状态变化或权限撤销均 fail-closed。
- 审批错误使用 `portal.approval.*`，不得再伪装为权限不足。
- Seed 切换到企业身份后应把 Profile 改为 `different-subject`，不修改代码。
